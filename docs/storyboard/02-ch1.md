### 장면 2. 문제 — 운영 DB 속의 표 [scrub · 3 step]
#### step 1
- 텍스트: 주문이 늘수록 손으로 세는 시간도 늘어요. 주니가 묻자 석 리드는 CSV의 출처부터 보여 줬어요.
- 대사:
  - 주니(당황): "이거 어떻게 해요?"
  - 석 리드: "운영 DB에 다 있어요. 작은 질문부터 SQL로 물어봐요."
- 화면: 석 리드의 책상 앞. 주니 손에 파일 아이콘 '주문내역.csv'. 석 리드 모니터에 원통 모양 노드 '운영 DB'. 원통에서 파일 아이콘으로 실선 화살표, 라벨 '내보내기'.
- 모션: 파일 아이콘에서 화살표가 거꾸로 거슬러 올라가며 그려져 원통 '운영 DB'에 닿고, 닿는 순간 화살표 방향이 '운영 DB → CSV'로 확정된다. (CSV의 출처)

#### step 2
- 텍스트: 바구니의 주문·상품 정보는 데이터베이스(Database, 데이터를 정리해 저장하고 꺼내 쓰게 해 주는 시스템)에 표 여러 개로 나뉘어 담겨 있어요. 표 하나하나는 테이블(Table, 엑셀 시트 같은 표)이라고 해요. 장사에 쓰는 이 데이터베이스를 '운영 DB'라고 불러요(DB는 데이터베이스의 줄임말).
- 화면: 원통 '운영 DB'의 뚜껑이 열려 있고, 안에서 테이블 카드 두 장이 위로 나와 있다 — 'orders (주문)', 'products (상품)'.
- 모션: 원통 뚜껑이 열리고 테이블 카드 두 장이 차례로 위로 올라와 나란히 놓인다. (DB 안에 테이블이 들어 있다는 것)

#### step 3
- 텍스트: orders 테이블의 가로 한 줄이 행(Row, 데이터 한 건)이고, 세로 한 줄이 열(Column, 데이터의 항목)이에요. 옆의 products 테이블과는 product_id라는 같은 열을 나눠 갖고 있죠.
- 화면: 왼쪽 orders 표(위 공통 데이터 10행 전부, 캡션 'orders · 6월 1일부터의 주문만 · 일부 열'), 오른쪽 products 표(4행). orders의 2001 행에 가로 강조 띠 + 라벨 '행 = 주문 한 건', qty 열에 세로 강조 띠 + 라벨 '열 = 항목'. 두 표의 product_id 열에 같은 점선 테두리.
- 모션: 가로 띠가 2001 행을 왼쪽에서 오른쪽으로 훑고, 이어서 세로 띠가 qty 열을 위에서 아래로 훑는다. 마지막에 두 표의 product_id 열에 점선 테두리가 동시에 그려진다.

### 장면 3. 시도와 실패 ① — 첫 SQL은 통했어요 [scrub · 4 step]
#### step 1
- 텍스트: SQL(Structured Query Language, 데이터베이스에 데이터를 묻고 다루는 언어)로 쓴 질문 하나를 쿼리(Query, 데이터베이스에 보내는 질문)라고 해요. SELECT는 '보여 줘', FROM은 '어느 표에서'예요.
- 화면: 왼쪽 코드 창
  ```sql
  SELECT *
  FROM orders;
  ```
  오른쪽 orders 표 10행 전부, 모든 행 보통 밝기(캡션 'orders · 6월 1일부터의 주문만'). 코드 창 옆 작은 풀이 '* = 모든 열'.
- 모션: 코드가 한 글자씩 써진다(스크롤 연동). `FROM orders` 타이핑이 끝나는 순간 orders 표 전체 테두리가 한 번 강조된다. (질문이 가리키는 표)

#### step 2
- 텍스트: WHERE는 조건이에요. '주문 날짜가 어제인 것만'이라고 적자 6월 2일 주문 5건만 남았어요.
- 화면: 코드 창
  ```sql
  SELECT *
  FROM orders
  WHERE DATE(ordered_at) = CURRENT_DATE - 1;  -- 어제(6/2)
  ```
  표에서 2004·2005·2006·2007·2008 행은 강조 테두리, 나머지 2001·2002·2003·2009·2010 행은 흐림(불투명도 0.65 — 흐려도 빠진 이유인 날짜는 읽히게, 대비 4.5:1 이상) + 행 끝 '제외' 라벨. 캡션 '이야기 속 오늘은 6월 3일'. 코드 창 옆 작은 풀이 'CURRENT_DATE - 1 = 오늘의 하루 전 · -- 뒤는 사람이 읽는 메모(주석)'.
- 모션: WHERE 줄이 타이핑되는 동안 ordered_at 열을 위에서 아래로 훑는 선이 내려가며, 6/2가 아닌 행이 지나가는 순서대로 흐려진다.

#### step 3
- 텍스트: GROUP BY는 같은 값끼리 묶어요. 상품별로 묶고 SUM(qty)로 수량을 더하니, 상품마다 숫자 하나로 모였어요.
- 대사: 주니(집중): "어제는 모두 9개! P1이 4개로 제일 많아요."
- 화면: 코드 창
  ```sql
  SELECT product_id, SUM(qty) AS 판매개수
  FROM orders
  WHERE DATE(ordered_at) = CURRENT_DATE - 1
  GROUP BY product_id;
  ```
  결과 표: P1 4 / P2 2 / P3 1 / P4 2. 코드 창 옆 작은 풀이 'SUM = 더하기 · AS = 결과 열에 붙이는 이름'. 결과 표 옆에 주니의 말풍선.
- 모션: 강조된 5행이 product_id별로 미끄러져 모인다(P1 묶음 = 2004·2006). 각 묶음의 qty 칸 숫자가 하나로 합쳐진다(P1: 1 + 3 → 4, 나머지 묶음은 한 행이라 그대로). 합쳐진 뒤 나머지 칸은 사라지고 결과 표 4행만 남는다.

#### step 4
- 텍스트: 그런데 대표님은 P1이 뭔지 모르시겠죠. 조인(JOIN, 두 테이블을 같은 열 값끼리 이어 붙이는 것)으로 products 테이블의 상품 이름을 붙였어요.
- 대사: 윤 대표: "수세미가 제일 잘 나가네요!"
- 화면: 코드 창
  ```sql
  SELECT orders.product_id, name, SUM(qty) AS 판매개수
  FROM orders
  JOIN products ON orders.product_id = products.product_id
  WHERE DATE(ordered_at) = CURRENT_DATE - 1
  GROUP BY orders.product_id, name;
  ```
  결과 표: P1 수세미 4 / P2 칫솔 2 / P3 주방세제 1 / P4 고무장갑 2. 결과 표 오른쪽에 products 표가 붙어 있고, product_id가 같은 칸끼리 연결선 4개(P1↔P1, P2↔P2, P3↔P3, P4↔P4). 주니 어깨 너머로 윤 대표가 결과 표를 들여다보고, 그 위에 윤 대표 말풍선.
- 모션: products 표가 오른쪽에서 들어와 product_id가 같은 칸끼리 선으로 이어지고, 선을 따라 name 값이 결과 표의 product_id 바로 오른쪽 새 열로 옮겨진다.

### 인터랙션: SQL 실행기
- 위치: 장면 3 다음 (방금 본 SELECT·WHERE·GROUP BY·JOIN을 직접 써 보고, 쓴 쿼리가 어떤 순서로 처리되는지 눈으로 보는 자리. 핀 고정 없이 일반 스크롤 흐름 안의 블록)
- 조작:
  - 구성(데스크톱): 왼쪽 위에 실험 버튼 6개 → 쿼리 편집기 → 실행 조절 버튼 3개와 상태 문구 → (오류일 때) 오류 상자, 왼쪽 아래에 실행 기록. 오른쪽에 '처리 과정' 그림(캡션 '연습용 주문 10건 · 이야기 속 오늘은 6월 3일'). 맨 아래 전체 폭으로 도움말 '이 실행기가 알아듣는 SQL'.
  - 구성(모바일): 실험 버튼 → 편집기(화면 폭 꽉 차게) → 실행 조절 → 오류 상자 → 처리 과정 그림 → 실행 기록 → 도움말 순서로 세로로 쌓는다.
  - 편집기: 진짜 `<textarea>`(라벨 'SQL 쿼리 · 고쳐 써도 돼요', 고정폭 글꼴, 맞춤법 검사·자동 대문자·자동 고침 끔, 합자 끔 — `>=`가 `≥`로 보이지 않게). 처음엔 장면 3 마지막 쿼리가 들어 있다:
    ```sql
    SELECT orders.product_id, name, SUM(qty) AS 판매개수
    FROM orders
    JOIN products ON orders.product_id = products.product_id
    WHERE DATE(ordered_at) = CURRENT_DATE - 1  -- 어제(6/2)
    GROUP BY orders.product_id, name;
    ```
    왼쪽 줄 번호 칸에 지금 처리 중인 절의 첫 줄에 ▶ 표시(줄 번호도 굵게). 편집기 안에서는 그 절의 글자만(예: 한 줄 쿼리 `select … from orders where qty >= 2`의 `where qty >= 2`만) 강조색 옅은 바탕 + 강조색 밑줄로 칠한다(색만으로 구분하지 않음 — ▶와 밑줄). 칠하기는 textarea 뒤에 같은 글자를 투명하게 깐 '거울' 층으로 하고, textarea의 가로 스크롤을 따라간다. 처리 중인 절이 가로 스크롤 너머에 있으면 편집기가 그 절이 보이게 저절로 가로로 옮겨 간다. 오류 줄에는 ✕ 표시와 그 줄 전체에 실패색 띠. 줄바꿈하지 않고 편집기 안에서만 가로 스크롤한다(데스크톱에선 처음 쿼리의 가장 긴 줄까지 다 보이게 왼쪽 칸을 조금 넓게, 편집기 글자 13px). Tab 키는 가로채지 않는다(다음 컨트롤로 포커스 이동). 글자를 고치면 실행이 '처음부터' 상태로 돌아간다. 타이핑은 선택이고, 실험 버튼만으로 모든 내용을 볼 수 있다.
  - 실험 버튼(`<button>`, 지금 편집기 내용과 같은 버튼은 `aria-pressed="true"`로 눌린 모양). 누르면 편집기 내용이 바뀌고, 실행은 처음부터 상태가 되며, 버튼 아래에 한 줄 설명이 나온다(자동 실행하지 않음).
    - 전부 보기 (SELECT *): `SELECT *` / `FROM orders;` — "가장 단순한 쿼리예요. FROM이 꺼낸 주문이 거르지도 묶지도 않은 채 그대로 결과가 돼요."
    - 어제만 보기 (WHERE 넣기): 위 쿼리 + `WHERE DATE(ordered_at) = CURRENT_DATE - 1;  -- 어제(6/2)` — "WHERE 줄을 넣었어요. 실행하면 어제 주문이 아닌 행에 ✕ 제외가 붙어요."
    - 상품별로 묶기 (GROUP BY): 장면 3 step 3의 쿼리 — "GROUP BY가 같은 product_id끼리 모으고, SUM(qty)이 묶음 안의 qty를 더해 숫자 하나로 합쳐요."
    - 상품 이름 붙이기 (JOIN): 처음 쿼리와 같음 — "JOIN 줄이 products 표에서 상품 이름을 가져와요. 쓰기는 SELECT가 먼저지만, 처리는 FROM부터예요."
    - 매출로 바꾸기 (SUM(qty * price)): 처음 쿼리에서 `SUM(qty) AS 판매개수`만 `SUM(qty * price) AS 매출`로 — "개수 대신 개수 × 개당 가격을 더해요. 한 줄만 바뀌었는데 결과 열이 달라져요."
    - 일부러 틀려 보기 (GROUP BY 빼기): 처음 쿼리에서 GROUP BY 줄을 지우고 세미콜론을 WHERE 줄 주석 앞으로 — "GROUP BY 줄을 지웠어요. ▶ 실행을 누르면 무엇이 문제인지 알려 줘요."
  - 실행 조절(모두 `<button>`): **▶ 실행**(한 단계씩 자동으로 이어 재생, 재생 중엔 '⏸ 멈춤'으로 바뀌어 누르면 그 자리에서 멈춤. 끝까지 간 뒤 누르면 처음부터 다시) / **한 줄씩**(다음 단계 하나만 처리. 재생 중이면 멈추고, 끝난 뒤 누르면 첫 단계부터) / **처음부터**(실행 전 상태로). 옆 상태 문구: '⏸ 아직 실행 전이에요' / '▶ 실행 중 · 2/5단계' / '⏸ 멈춤 · 3/5단계' / '✓ 실행 끝 · 5단계를 모두 처리했어요' / (오류 상자가 떠 있을 때) '✕ 쿼리를 고치면 실행할 수 있어요'. ⏸ 멈춤은 다음 단계로 넘어가지 않게 할 뿐, 이미 재생 중인 단계의 짧은 움직임(1초 이내)은 끝까지 마친다.
  - 처리 순서: 쓴 순서가 아니라 SQL의 논리적 처리 순서로 단계가 진행된다. FROM → (JOIN) → (WHERE) → (GROUP BY) → SELECT. 그래서 처음 쿼리는 2줄 → 3줄 → 4줄 → 5줄 → 1줄 순서로 ▶가 옮겨 간다. 단계마다 기본 재생 시간은 약 0.6~0.8초이고, 다음 단계 전에 0.2초 쉰다.
  - 도움말 '이 실행기가 알아듣는 SQL'(항상 보임): 첫 문장 "SQL은 쓴 순서가 아니라 FROM → JOIN → WHERE → GROUP BY → SELECT 순서로 처리돼요(실제 데이터베이스는 더 똑똑하게 순서를 바꾸기도 해요)." 이어서 목록:
    - `SELECT *` 또는 `SELECT 열, 열` — 열: order_id, product_id, qty, price, ordered_at, name (`orders.qty`처럼 표 이름을 붙여도 됨)
    - `SUM(qty)` · `SUM(qty * price)` · `COUNT(*)` — `AS 판매개수`처럼 결과 열 이름을 붙일 수 있음
    - `FROM orders`
    - `JOIN products ON orders.product_id = products.product_id` (없어도 됨)
    - `WHERE` 조건 하나 (없어도 됨): `DATE(ordered_at) = CURRENT_DATE - 1` · `product_id = 'P1'` · `qty >= 2`
    - `GROUP BY 열, 열` (없어도 됨) — SUM·COUNT와 함께 SELECT한 보통 열은 모두 여기에 적음
    - `SELECT` 같은 낱말과 열·표 이름은 대소문자를 가리지 않지만, 작은따옴표 안의 값은 가림(`'P1'`과 `'p1'`은 다름), `--` 뒤는 메모(주석)라 실행하지 않음, 맨 끝 `;`는 있어도 없어도 됨
  - 해석기가 실제로 받아 주는 범위(도움말보다 조금 너그럽다): `INNER JOIN`, ON의 양쪽 순서 바꾸기, `orders.*`·`products.*`, `COUNT(열)`(이 데이터엔 빈 값이 없어 `COUNT(*)`와 같음), `SUM(price)`·`SUM(price * qty)`, WHERE의 비교 기호 `= <> != > >= < <=`(글자 열은 `= <> !=`만), `CURRENT_DATE`·`CURRENT_DATE - n`(오늘에서 n일 전), `name = '수세미'`(JOIN이 있을 때), GROUP BY만 쓰고 SUM·COUNT가 없는 쿼리, SUM·COUNT만 쓰고 GROUP BY가 없는 쿼리(남은 행 전체가 한 묶음 → 결과 1행). 그 밖의 문법은 실행하지 않고 오류 상자로 안내한다(아래 '오류').
  - 결과 영역 접근성: 그림(SVG)은 `aria-hidden`이고, 같은 내용을 실행 기록(`<ol>`)이 글로 담는다. 실행 기록이 한 줄 늘 때마다 `aria-live="polite"` 영역이 그 줄을 읽어 준다. 실험 버튼 아래 한 줄 설명은 따로 `aria-live="polite"`라 버튼을 누르면 그 설명을 읽고, 처음부터를 눌러도 다시 읽지 않는다(처음부터는 실행 기록 영역을 비우기만 한다). 모션 줄이기에서 ▶ 실행을 누르면 모든 기록을 한 번에 읽어 준다. 오류 상자는 `role="alert"`.
- 상태별 결과:
  - 실행 전: 처리 과정 칸은 비어 있고 가운데에 "▶ 실행이나 한 줄씩을 누르면, 여기에서 표가 단계마다 바뀌어요." 실행 기록 칸엔 "아직 실행한 줄이 없어요." (오류 상자가 떠 있으면 그림 칸 문구는 "쿼리를 고치면 여기에서 다시 처리 과정을 볼 수 있어요.")
  - 처리 과정 그림: 표 하나가 단계마다 모양을 바꾼다. 행마다 강조색 옅은 띠(데이터 = 강조색), 글자는 본문색. 표 위 제목이 단계마다 바뀐다.
    - FROM: 제목 'orders · 10행'. orders 표의 5열(order_id, product_id, qty, price, ordered_at) 머리글과 10행이 위에서 살짝 내려오며 차례로 나타난다(약 0.6초).
    - JOIN: 제목 'orders + products의 name · 10행'. orders 표 아래에 products 표(product_id, name 4행)가 오른쪽에서 밀려 들어오고(0.25초), 각 주문 행의 name 칸이 products 표의 같은 product_id 행에서 위로 날아올라 orders 표 맨 오른쪽 새 열로 붙는다(행마다 조금씩 늦게, 약 0.5초). products 표의 name 열과 orders 표의 name 열은 같은 세로줄에 있어 이름이 곧장 위로 올라간다.
    - WHERE: 제목 'WHERE 뒤 · 5행 남음'. products 표가 사라지고, 조건 열(날짜 조건이면 ordered_at, `product_id = 'P1'`이면 product_id, `qty >= 2`면 qty) 머리글 아래에서 강조색 선이 위에서 아래로 훑어 내려간다(0.5초). 선이 지나가는 순서대로 조건에 맞지 않는 행이 흐려지고(불투명도 0.65, 값은 읽히게) '✕ 제외' 꼬리표(실패색 테두리 + 글자)가 붙는다. 꼬리표 자리: JOIN이 없으면 표 오른쪽 밖, JOIN이 있으면 name 칸 위(조건이 name이면 order_id 칸 위). 처음 쿼리에선 2001·2002·2003·2009·2010이 제외된다.
    - GROUP BY: 제목 'GROUP BY 뒤 · 4묶음'. ① 흐린 행이 사라지고, 남은 행이 묶음 순서(product_id 순)로 다시 줄을 서며 묶음 사이에 틈이 생기고 묶음마다 강조색 손그림 테두리가 둘러진다(P1 묶음 = 2004·2006). ② 테두리가 사라지며 묶음 안의 행들이 한 줄 자리로 겹쳐 모인다. GROUP BY 열의 칸(product_id, name)은 같은 자리로 모여 하나가 되고, 합칠 값의 칸(SUM(qty)이면 qty, SUM(qty * price)면 qty와 price)은 오른쪽 새 열 'SUM(qty)' 자리로 날아간다. 나머지 칸(order_id, ordered_at 등)은 사라진다. ③ 모인 칸이 합친 값 하나로 바뀐다(P1 4, P2 2, P3 1, P4 2, 합친 값은 굵게). 전체 약 0.8초.
    - SELECT: 제목 '결과 · 4행'. SELECT에 적은 열만 적은 순서대로 남아 왼쪽부터 다시 자리 잡고, 머리글이 별칭으로 바뀐다(SUM(qty) → 판매개수). 결과 표에 강조색 손그림 테두리가 그려진다(약 0.6초). GROUP BY가 없는 쿼리는 이 단계에서 먼저 흐린 행이 사라지고 남은 행이 위로 붙는다. SUM·COUNT만 있고 GROUP BY가 없으면 남은 행 전체가 한 줄로 모여 합친 값 하나가 된다.
  - 실행 기록 문구 형식: `{N}줄 {절}: {설명}`(절이 여러 줄에 걸치면 `1~2줄`). 처음 쿼리의 기록:
    1. "2줄 FROM orders: orders 표에서 주문 10건을 꺼냈어요."
    2. "3줄 JOIN products: product_id가 같은 products 행을 찾아 10건 모두에 상품 이름(name)을 붙였어요."
    3. "4줄 WHERE: 주문 날짜가 어제(6/2)인 주문만 남겨요. 10건 → 5건, 2001·2002·2003·2009·2010번은 제외."
    4. "5줄 GROUP BY: orders.product_id, name 값이 같은 주문끼리 묶었어요. 5건 → 4묶음 (P1·수세미 2건, P2·칫솔 1건, P3·주방세제 1건, P4·고무장갑 1건). 묶음마다 SUM(qty) 값을 계산해 한 줄로 합쳤어요."
    5. "1줄 SELECT: product_id, name, 판매개수 열만 남겨 결과 4행을 만들었어요. 결과: P1 수세미 4 / P2 칫솔 2 / P3 주방세제 1 / P4 고무장갑 2"
    - 제외된 행이 6건 이상이면 번호 대신 'n건은 제외.', 하나도 없으면 ', 빠진 주문이 없어요.' 묶음이 5개 이상이면 묶음 목록을 생략한다. 결과가 4행 이하면 결과 값을 기록에 함께 적는다. `SELECT *` 하나뿐이면 SELECT 기록은 "*는 모든 열이라 열을 그대로 두고 결과 n행을 만들었어요." GROUP BY 없이 SUM·COUNT만 쓰면 "GROUP BY가 없어서 남은 n건을 한 묶음으로 보고 … 값을 계산했어요."가 앞에 붙는다. 더할 행이 없으면 SUM은 NULL로 보이고 "더할 행이 없으면 SUM은 NULL(값 없음)이 돼요."를 덧붙인다.
    - WHERE 조건 풀이: 날짜 → '주문 날짜가 어제(6/2)인'(0일 전 '오늘', 2일 이상 'n일 전'), 비교 → '{열} 값이 {값}인 / {값} 이상인 / {값} 이하인 / {값}보다 큰 / {값}보다 작은 / {값} 말고 다른'.
  - 실험별 결과(모두 공통 데이터에서 해석기가 계산한 값):

    | 실험 | 처리 단계 | 결과 |
    |---|---|---|
    | 전부 보기 | FROM → SELECT | 10행, 5열 (2001~2010) |
    | 어제만 보기 | FROM → WHERE → SELECT | 5행: 2004, 2005, 2006, 2007, 2008 |
    | 상품별로 묶기 | FROM → WHERE → GROUP BY → SELECT | product_id, 판매개수: P1 4 / P2 2 / P3 1 / P4 2 |
    | 상품 이름 붙이기 | FROM → JOIN → WHERE → GROUP BY → SELECT | product_id, name, 판매개수: P1 수세미 4 / P2 칫솔 2 / P3 주방세제 1 / P4 고무장갑 2 |

  - 오류: 해석기는 예외를 던지지 않고 오류 상자를 띄운다. 상자: 제목 '✕ {N}줄에서 멈췄어요'(줄을 모르면 '✕ 실행하지 못했어요') + 설명 한두 문장 + (있으면) '비슷한 말: FROM' + (있으면) '이렇게 써 보세요: `…`'. 편집기의 그 줄에 ✕와 실패색 띠. 그림은 바뀌지 않고, 실행 기록은 비어 있다. 주요 경우:
    - 일부러 틀려 보기(집계 + 보통 열 + GROUP BY 없음): 1줄 ✕, "SUM·COUNT로 합친 값과 보통 열(orders.product_id, name)을 함께 SELECT하면, 그 보통 열을 GROUP BY에 적어야 해요. 무엇끼리 묶을지 모르면 한 줄에 어느 행의 값을 쓸지 정할 수 없거든요. 실제 데이터베이스도 대부분 이 쿼리를 오류로 막아요." / 이렇게 써 보세요: `GROUP BY orders.product_id, name`. GROUP BY에 일부 열만 적었을 때도 빠진 열을 짚어 같은 안내를 한다.
    - 철자 틀림: 절 키워드·열·표 이름이 한두 글자 다르면(빠짐·더함·바꿈·자리 바뀜) '비슷한 말'을 짚는다. 예: `FORM orders` → "'FORM' — 이 실행기가 모르는 말이에요." / 비슷한 말: FROM. `qyt` → "'qyt' 열은 없어요. 쓸 수 있는 열: …" / 비슷한 말: qty.
    - JOIN 없이 name·products.열 → "name 열은 products 표에 있어요. JOIN 줄을 넣어야 쓸 수 있어요." + JOIN 줄 모양.
    - JOIN과 함께 표 이름 없는 product_id → "JOIN을 하면 product_id가 orders와 products 두 표에 모두 있어서 어느 쪽인지 정할 수 없어요. 앞에 표 이름을 붙여 주세요." / `orders.product_id`.
    - 모르는 절·문법(ORDER BY, HAVING, LIMIT, LEFT JOIN, DISTINCT, INSERT·UPDATE·DELETE 등) → "이 실행기는 ORDER BY까지는 몰라요. 알아듣는 건 SELECT · FROM · JOIN · WHERE · GROUP BY예요." / AND·OR → 조건은 하나만 / AVG 같은 함수 → SUM과 COUNT만 / 절 순서가 틀림 → "WHERE 줄은 GROUP BY 줄보다 앞에 와야 해요. 쓰는 순서: …" / 절이 두 번 / FROM 없음 / FROM products / JOIN 모양이 다름 / 중간의 세미콜론 / 닫히지 않은 작은따옴표 / 큰따옴표(`"P1"`, `AS "판매개수"`) → "큰따옴표(")는 이 실행기가 몰라요. 글자 값은 작은따옴표로 감싸고, 결과 열 이름(AS 뒤)은 따옴표 없이 한 단어로 써요." / 따옴표 빠진 글자 값(`product_id = P1` → `product_id = 'P1'`)·따옴표 친 숫자·숫자 열을 다른 열과 비교(`qty = price` → 조건 모양 안내) / 날짜 조건 모양·너무 먼 날(`CURRENT_DATE - n`의 n이 9999 초과) / 쉼표 빠짐(`qty price`, `product_id SUM(qty)`) → 이렇게 써 보세요: `product_id, SUM(qty)   ·   SUM(qty) AS 판매개수` / 괄호 짝이 안 맞음(`SUM(qty`, `SUM(qty))`) / AS 뒤 이름 빠짐(`qty AS FROM`) / `SELECT *`와 집계를 함께 / 모르는 기호(`≥`·`≤`·`≠`·전각 `＊` 등은 비슷한 말로 `>=`·`<=`·`<>`·`*`를 짚는다).
    - 철자 틀림을 다른 문법으로 오해하지 않는다: `FROM order`·`order.qty`는 ORDER BY가 아니라 표 이름 오타로 보고 '비슷한 말: orders'(ORDER는 바로 뒤에 BY가 올 때만 ORDER BY로 본다). `GROUPBY`·`GROUP_BY` → 비슷한 말 'GROUP BY'. `product`·`product-id` → 비슷한 말 'product_id'. GROUP BY 안내의 바른 모양은 JOIN이 있으면 `GROUP BY orders.product_id, name`, 없으면 `GROUP BY product_id`.
- 안내 문구: "쿼리를 고쳐 쓰거나 실험 버튼을 눌러 보고, **▶ 실행**으로 쿼리가 표를 어떻게 바꾸는지 지켜보세요. 진짜 데이터베이스가 아니라 연습용 주문 10건으로 처리해요." 블록 맨 아래 고지: "※ 단순화한 모델이에요. 진짜 SQL 엔진이 아니라 위 목록만 알아듣는 연습용 실행기예요. 날짜를 쓰는 문법은 데이터베이스마다 조금씩 달라요. 결과는 보기 쉽게 정렬했어요(실제로는 ORDER BY로 순서를 정해요)." (문구 속 10건·6월 3일은 공통 데이터에서 만든다.)
- 모션 축소 모드: ▶ 실행을 누르면 애니메이션 없이 곧바로 마지막(SELECT) 상태의 결과 표가 보이고, 실행 기록에 모든 단계가 한꺼번에 적힌다(편집기 ▶는 SELECT 줄). 재생 중에 페이지의 '모션 줄이기'를 켜도 남은 단계를 건너뛰고 같은 마지막 상태가 된다. 한 줄씩은 단계마다 그 단계의 정지 그림으로 바로 바뀐다(WHERE 단계는 흐린 행 + '✕ 제외', GROUP BY 단계는 묶음마다 한 줄로 합쳐진 표). 실행 기록 줄이 나타날 때의 짧은 등장 모션도 끈다. 문구·aria-live는 기본 모드와 같다.

### 장면 4. 시도와 실패 ② — 운영 DB에 던진 큰 쿼리 [scrub · 3 step]
#### step 1
- 텍스트: 신이 난 주니는 더 큰 질문을 던졌어요. 문을 연 날부터의 주문 전부에 상품·고객을 이어 붙여 고객별·상품별 매출을 구하는 쿼리였죠.
- 대사:
  - 석 리드: "이걸 운영 DB에 직접요? 음…"
  - 주니(집중): "일단 해 볼게요!"
- 화면: 코드 창
  ```sql
  SELECT customers.name, products.name, SUM(qty * price) AS 매출
  FROM orders  -- 기간 조건 없음: 전체 기간
  JOIN products ON orders.product_id = products.product_id
  JOIN customers ON orders.customer_id = customers.customer_id
  GROUP BY customers.customer_id, customers.name, products.name;
  ```
  코드 창 위 [중지] 버튼 줄 왼쪽에 작은 풀이 'customers = 고객 테이블'(코드 타이핑이 끝나면 나타남). 코드 창 오른쪽에 게이지 '운영 DB 부하' 15%(초록 구간). 그 아래 결제 카드 자리(비어 있음). 석 리드가 주니 뒤에서 화면을 보고 있다.
- 모션: 긴 쿼리가 한 글자씩 써진다(스크롤 연동). 게이지는 15%에 머문다.

#### step 2
- 텍스트: 쿼리가 쌓인 주문을 전부 훑고 고객·상품 표까지 이어 붙이느라 운영 DB가 바빠졌어요. 그 일에 힘을 쏟는 사이, 손님들의 결제 처리가 느려졌어요.
- 대사: 태오: "결제 페이지가 왜 이렇게 느리죠?"
- 화면: 운영 DB 원통 안의 orders 표 전체를 굵은 빛줄기가 덮고 있다. 게이지 바늘이 빨간 구간 98%, 라벨 '과부하'. 게이지 아래 결제 카드 3장 '결제 #2011 ⏸ 대기', '결제 #2012 ⏸ 대기', '결제 #2013 ⏸ 대기'(회색). 화면 오른쪽 끝에서 태오가 노트북을 들고 다가오고, 그 위에 태오 말풍선. 게이지 아래 작은 캡션: '※ 알아보기 쉽게 부하를 크게 그렸어요. 가게가 작을 땐 티가 덜 나도, 데이터가 쌓일수록 실제로 생기는 일이에요.'
- 모션: 빛줄기가 표를 위에서 아래로 훑을수록(스크롤 진행에 비례) 게이지 바늘이 15% → 98%로 오르고, 결제 카드가 하나씩 ⏸ 상태로 쌓인다. (무거운 분석이 짧은 결제 작업을 밀어낸다)

#### step 3
- 텍스트: 주니가 급히 쿼리를 멈추자 밀렸던 결제가 하나씩 끝났어요. 질문 자체보다, 그 질문을 던진 장소가 문제였죠.
- 대사: 주니(당황): "제, 제 쿼리 때문이었나 봐요!"
- 화면: 태오가 노트북을 들고 주니 책상 옆에 서 있다. 눌린 [■ 중지] 버튼 옆에 '쿼리 중지됨 ✕'. 게이지 15%. 결제 카드 3장 '결제 #2011 ✓ 완료', '#2012 ✓ 완료', '#2013 ✓ 완료'(초록). 주니 표정: 당황.
- 모션: 코드 창의 [중지] 버튼이 눌리면 빛줄기가 사라지고 게이지 바늘이 98% → 15%로 내려가며, 결제 카드의 ⏸가 위에서부터 차례로 ✓로 바뀐다.

### 장면 5. 개념 — 비유: 계산대와 장부 정리 [scrub · 3 step]
#### step 1
- 텍스트: 가게 계산대를 떠올려 보세요. 한 명 계산은 금방 끝나지만, 그 일이 하루 종일 이어져요.
- 화면: 손그림 계산대와 계산원, 줄 선 손님 4명. 앞의 손님 2명 위에 ✓.
- 모션: 손님이 한 명씩 계산대로 다가와 ✓가 붙고 빠져나가면 다음 손님이 앞으로 온다. (짧은 일이 아주 많이, 빠르게)

#### step 2
- 텍스트: 계산원이 계산대에서 1년치 장부 정리를 시작하면 어떨까요? 그동안 손님들은 한참을 기다려야 해요.
- 화면: 계산대 위에 두꺼운 장부 '1년치 장부'. 계산원이 장부를 넘기고 있고, 줄 선 손님 4명 위에 모두 ⏸.

#### step 3
- 텍스트: 그래서 장부 정리는 보통 뒤쪽 사무실에서 해요. 둘 다 가게 숫자를 다루지만 일의 성격이 달라요.
- 화면: 화면이 둘로 나뉜다. 왼쪽 '계산대' — 줄이 다시 움직이고 손님 위 ✓. 오른쪽 '뒤쪽 사무실' — 책상 위에 '1년치 장부'.
- 모션: 장부가 계산대에서 오른쪽 사무실 책상으로 옮겨지고, 옮겨지는 순간 계산대 줄이 다시 움직이며 ⏸가 ✓로 바뀐다.

### 장면 6. 개념 — 정의와 쇼핑몰 예시: OLTP와 OLAP [scrub · 3 step]
#### step 1
- 텍스트: 계산대 같은 일을 OLTP(Online Transaction Processing, 짧은 읽기·쓰기를 아주 많이, 빠르게 처리하는 방식)라고 해요. 바구니의 운영 DB가 하는 일로, 주문 저장처럼 한 번에 몇 행만 건드려요.
- 화면: 원통 '운영 DB (OLTP)'와 그 안의 orders 표. 짧은 화살표 3개가 각각 행 하나씩만 가리킨다 — '새 주문 저장 · 1행 쓰기', '내 주문 보기 · 1행 읽기', '주문 취소 · 1행 고치기'. 가리킨 행마다 ✓.
- 모션: 짧은 화살표가 번갈아 빠르게 행 하나씩 찍고 지나가며, 찍힌 행에 ✓가 붙는다.

#### step 2
- 텍스트: 장부 정리 같은 일은 OLAP(Online Analytical Processing, 많은 행을 훑어 모으고 계산하는 분석 방식)이에요. '고객별·상품별 전체 매출'처럼 한 번에 아주 많은 행을 읽어요.
- 화면: 같은 orders 표 전체를 빛줄기 하나가 덮고 있다. 표 오른쪽에 '상품별 매출' 막대 4개(수세미·칫솔·주방세제·고무장갑, 숫자 없이 길이만). 라벨 'OLAP'.
- 모션: 빛줄기가 모든 행을 위에서 아래로 한 번 훑은 뒤, 훑은 값들이 오른쪽 막대 4개로 모여 막대가 자란다.

#### step 3
- 텍스트: 같은 DB에서 무거운 OLAP을 돌리면 OLTP가 쓸 힘을 빼앗을 수 있어요. 실제로는 데이터 크기·쿼리 모양·컴퓨터 성능에 따라 영향이 달라요.
- 화면: 비교 표.

  |  | OLTP (운영용) | OLAP (분석용) |
  |---|---|---|
  | 바구니 예시 | 주문 저장, 결제 | 고객별·상품별 전체 매출 |
  | 한 번에 다루는 행 | 몇 개 | 아주 많이 |
  | 중요한 것 | 빠른 응답 | 많이 훑는 힘 |

  표 아래 캡션 '※ 단순화한 비교예요.' 표 옆에 작은 게이지 아이콘과 라벨 '같은 DB에서 함께 돌리면 → 부하'.
- 모션: 비교 표가 한 줄씩 채워진다(바구니 예시 → 한 번에 다루는 행 → 중요한 것). 마지막 줄이 채워진 뒤 게이지 아이콘 라벨이 나타난다.

### 장면 7. 해결 — 운영 DB는 계산대에 맡기기 [scrub · 3 step]
#### step 1
- 텍스트: 주니는 당장 지킬 규칙부터 세웠어요. 운영 DB에는 손님이 적은 시간에만, 짧은 기간만 물어보기로요.
- 화면: 주니의 노트북 옆에 포스트잇 3장 — '① 큰 분석은 운영 DB에서 멈추기', '② 손님 적은 시간에만', '③ 짧은 기간만 (어제 하루처럼)'. 노트북 화면 구석의 작은 게이지 '운영 DB 부하 15%'.
- 모션: 포스트잇이 ① → ② → ③ 순서로 한 장씩 붙는다. 게이지는 15%에 머문다.

#### step 2
- 텍스트: 파이프라인 맵에 운영 DB가 생겼어요. 앱의 주문이 쌓이는 곳이고, CSV도 여기서 내보낸 사본이었죠. 운영 DB에서 노트북으로 곧장 가는 '직접 쿼리' 점선엔 경고가 붙었어요.
- 화면: 파이프라인 맵 — 새 실선 [쇼핑몰 앱·웹] → [운영 DB (OLTP)] → [CSV 파일], 실선 [CSV 파일] → [주니의 노트북]은 그대로(앱 → CSV 실선은 사라짐). 그리고 [운영 DB (OLTP)]에서 [주니의 노트북]으로 빨간 경고 점선, 그 위 라벨 '직접 쿼리'와 경고 표시(게이지 아이콘 + 글자 '부하 경고'). 노드 수 4.
- 모션: 앱 → CSV 실선이 흐려져 사라지고, 앱 노드에서 새 실선이 뻗어 나가 그 끝에 운영 DB 노드가 손그림 선으로 그려진다. 운영 DB에서 CSV로 실선이 이어지고(CSV의 출처), 이어서 운영 DB에서 노트북으로 빨간 점선이 그려지고, 점선 가운데에 '직접 쿼리' 라벨, 운영 DB 쪽에 '부하 경고' 표시가 붙는다.

#### step 3
- 텍스트: 하지만 규칙만으로는 오래 못 버텨요. 주문도, 대표님의 질문도 매일 늘어날 테니까요.
- 대사:
  - 주니(집중): "분석용은 따로 둬야겠어요."
  - 석 리드: "운영 DB는 안 건드리고요? 어떻게 옮길지가 숙제네요."
- 화면: 석 리드의 책상 앞. 주니가 들고 있는 손그림 종이에 운영 DB 옆으로 연필 점선 상자 '분석용?'이 그려져 있다(장면 속 주니의 메모일 뿐, HUD 파이프라인 맵 노드가 아니다). 주니 표정: 집중.
- 모션: 연필 선이 운영 DB 옆에 점선 상자를 그리고, 상자 안에 '분석용?'이 써진다. (다음 챕터의 질문)

### 한 줄 요약
> SQL로 표에 질문하면 손으로 세지 않아도 되지만, 손님을 받는 운영 DB(OLTP)에서 무거운 분석(OLAP)을 돌리면 서비스가 느려질 수 있어요.

### 퀴즈
- 질문: 주니가 "분석용은 따로 둬야겠어요"라고 결론 내린 가장 큰 이유는 무엇일까요?
- 보기:
  1. 분석 쿼리가 운영 DB의 주문 기록을 고쳐 버릴 수 있어서 — ✕ 해설: 주니가 쓴 SELECT는 데이터를 읽기만 하고 바꾸지 않아요. 기록이 바뀐 게 아니라, 무거운 읽기가 운영 DB를 바쁘게 만든 게 문제였어요.
  2. 많은 행을 훑는 분석(OLAP)이 주문·결제처럼 빨라야 하는 운영 일(OLTP)의 힘을 빼앗기 때문에 — ✓ 해설: 맞아요. 전체 기간을 훑는 큰 쿼리가 운영 DB를 바쁘게 만드는 동안 손님의 결제가 기다려야 했어요. 일의 성격이 다르니 자리를 나누는 거예요.
  3. 운영 DB에는 상품 이름이 없어서 JOIN을 할 수 없기 때문에 — ✕ 해설: products 테이블이 운영 DB 안에 있었고, JOIN으로 이름을 잘 붙였어요.
  4. 운영 DB의 주문 숫자가 CSV보다 부정확해서 — ✕ 해설: CSV는 운영 DB에서 뽑은 사본이에요. 숫자가 틀린 게 아니라, 무거운 질문이 손님의 결제를 늦춘 게 문제였어요.
- 공통 해설: 같은 데이터라도 손님을 받는 일과 장부를 정리하는 일은 성격이 달라요. 그래서 다음 챕터에서 주니는 분석할 데이터를 운영 DB 밖으로 옮기는 방법을 찾아요.

### 카드 정의
- **J — Join(조인)**: 두 테이블에서 같은 열 값을 가진 행끼리 이어 붙여 하나의 결과 표로 합치는 연산
- **O — OLTP vs OLAP**: 짧은 읽기·쓰기를 빠르게 많이 하는 운영용 처리와 많은 행을 훑어 집계하는 분석용 처리의 구분

- 모션 축소 모드: 코드 타이핑 대신 각 step의 완성된 코드를 바로 보여 준다. 행 하이라이트·흐림은 그대로 정지 상태로 보여 주되 흐린 행에는 '제외' 글자 라벨을 붙인다. 게이지는 최종 값(15% / 98% '과부하' / 15%)을 숫자와 함께 정지 상태로 표시한다. 결제 카드는 ⏸ 대기 / ✓ 완료 아이콘과 글자로 상태를 구분한다. 장면 3 step 3의 '묶여서 합쳐지는' 과정은 왼쪽에 걸러진 5행, 오른쪽에 결과 4행을 나란히 놓고 사이에 'GROUP BY →' 화살표로 대신한다.

### 정확성 메모
- 화면 속 orders 테이블은 6월 1일부터의 주문만, 일부 열만 보여 준다(프롤로그의 첫날 주문 1001~1005 같은 예전 행은 생략). 어제(6월 2일) 주문은 화면에 모두 있으므로 '어제 9개'는 전체 데이터로도 맞는 답이다. 장면 4의 큰 쿼리는 화면에 나오지 않은 customer_id 열과 customers 테이블을 쓴다. 화면 고지: 장면 2 step 3·장면 3 step 1 표 캡션 'orders · 6월 1일부터의 주문만', 장면 4 step 1 풀이 'customers = 고객 테이블'.
- 날짜 조건 `DATE(ordered_at) = CURRENT_DATE - 1`은 PostgreSQL 방식의 문법이다. 실무에서는 인덱스를 쓰기 좋게 `ordered_at >= … AND ordered_at < …` 범위 조건으로 쓰는 경우가 많지만, 읽기 쉬운 쪽을 택했다. 데이터베이스마다 날짜 함수와 날짜 계산 문법이 다르다. 화면 고지: SQL 실행기 맨 아래 고지 "※ … 날짜를 쓰는 문법은 데이터베이스마다 조금씩 달라요."
- 결과 행 순서: ORDER BY가 없으면 결과 순서는 보장되지 않는다. 화면은 보기 쉽게 product_id·order_id 순으로 정렬했다. 화면 고지: SQL 실행기 같은 고지 "결과는 보기 쉽게 정렬했어요(실제로는 ORDER BY로 순서를 정해요)." 장면 3의 결과 표는 고지 없이 같은 정렬을 쓴다(실행기 고지가 같은 장면 묶음 안에 있음). 실행기의 결과 정렬: GROUP BY 결과는 묶은 열 값 순, 나머지는 order_id 순.
- 한국어 별칭(`AS 판매개수`, `AS 매출`)은 학습 편의를 위한 것이다. PostgreSQL에서는 따옴표 없이 쓸 수 있지만 데이터베이스에 따라 따옴표가 필요할 수 있다. 화면 고지 없음(SQL 문법 튜토리얼이 아니므로).
- `SELECT orders.*, products.name`처럼 표 이름을 붙인 열 지정(orders.product_id 등)은 두 표에 같은 이름의 열이 있을 때 헷갈리지 않게 하려는 것이다. 별도 설명 없이 코드에만 쓴다.
- 큰 쿼리로 결제가 느려지는 장면: 실제로는 데이터 크기, 쿼리 모양, 서버 사양, DB 설정에 따라 영향이 크게 다르고, 사용자 100명 규모의 작은 DB라면 티가 안 날 수도 있다. 부하가 결제를 늦추는 원리(CPU·메모리·디스크를 나눠 쓰는 경쟁, 잠금 등)도 '힘을 빼앗는다'로 줄였다. 결제는 완전히 멈추는 게 아니라 느려지는 것이므로 장면 4 텍스트는 '느려졌다'로 썼다. '차례를 기다린다' 같은 줄 서기 표현도 피했다. 대부분의 DB에서 읽기 쿼리가 쓰기를 줄 세워 막지는 않고, 자원을 나눠 쓰느라 함께 느려지기 때문이다. 계산대 비유의 '기다린다'는 비유 안에서만 쓴다. 화면 고지: 장면 4 step 2 캡션 '※ 알아보기 쉽게 부하를 크게 그렸어요…', 장면 6 step 3 텍스트 "실제로는 데이터 크기·쿼리 모양·컴퓨터 성능에 따라 영향이 달라요.".
- 기간: 바구니는 문을 연 지 얼마 안 된 가게(바이블 0-1)라서 '1년치 주문'은 아직 없다. 큰 쿼리는 '문을 연 날부터의 주문 전부'로 썼다. 계산대 비유의 '1년치 장부'는 일반적인 가게 이야기라 그대로 두었다.
- 큰 쿼리는 고객을 `customers.customer_id`로 묶는다. 이름으로만 묶으면 이름이 같은 고객이 하나로 합쳐지기 때문이다. `customers.name`은 SELECT하려고 GROUP BY에 함께 적었다(실행기 규칙과 같음). 상품은 이름이 겹치지 않는다고 보고 `products.name`으로 묶었다. 결과 열 두 개의 이름은 모두 name으로 나온다(표 이름은 결과 열 이름에 남지 않는다). PostgreSQL 기준으로는 올바른 쿼리지만, BigQuery처럼 결과 열 이름이 겹치면 오류를 내는 데이터베이스도 있다. 코드 창 폭 때문에 별칭(AS 고객, AS 상품)은 붙이지 않았고, 이 장면의 요점이 아니어서 고지하지 않았다. 기간 조건이 없다는 주석은 WHERE가 들어갈 자리인 FROM 줄 끝에 둔다.
- 데이터베이스를 '창고'로 부르지 않았다. Ch4·Ch8에서 웨어하우스(창고)가 분석용 저장소의 비유로 쓰이므로, 운영 DB와 섞이지 않게 하려는 것이다.
- OLTP/OLAP 정의와 비교 표는 단순화한 것이다. 두 일을 함께 처리하도록 설계된 데이터베이스도 있다. 화면 고지: 장면 6 step 3 비교 표 캡션 '※ 단순화한 비교예요.'
- 해결책(손님 적은 시간에만, 짧은 기간만)은 임시방편이다. 운영 DB의 읽기 전용 복제본을 두는 방법 등도 있지만 이 챕터에서는 다루지 않고, Ch2의 분석용 저장소로 이어간다. 화면 고지: 장면 7 step 3 텍스트 "규칙만으로는 오래 못 버텨요."
- 장면 2 step 2는 "바구니의 주문·상품 정보는 데이터베이스에 표 여러 개로 나뉘어 담겨 있어요"처럼 바구니의 데이터베이스(관계형)로 한정해 말한다. 모든 데이터베이스가 표로 저장하는 것은 아니기 때문이다(문서·키-값 방식 등). 화면 고지 없음(이 페이지가 다루는 운영 DB·웨어하우스가 표 중심이라 입문 단계에서 오해를 만들지 않음).
- 맵: 구현 맵(src/content/map.ts)을 따라 app → oltp 실선을 더하고, 프롤로그의 app → csv 실선을 oltp → csv로 바꿨다(csv → bi는 그대로). 장면 2 step 1(운영 DB → 주문내역.csv '내보내기')과 퀴즈 해설('CSV는 운영 DB에서 뽑은 사본')이 맵과 어긋나지 않게 하려는 것이다. oltp ⇢ bi 경고 점선('직접 쿼리')도 더했다. 경고 점선은 바이블 0-7의 'Ch1 직접 쿼리(점선, 부하 경고)'를 따른다.
- 한 주문 = 한 상품: 실제로는 주문 한 건에 여러 상품이 담기므로 주문 항목 테이블을 따로 두는 경우가 많다. JOIN·GROUP BY를 보여 주는 데 집중하려고 orders 한 행에 상품 하나만 두었다. 주문 항목 같은 '사건' 테이블은 Ch4 팩트 테이블에서 다시 다룬다. 화면 고지 없음.
- JOIN 장면의 순서: 장면 3 step 4는 이미 묶인 결과 4행에 상품 이름을 붙이는 모습으로 그렸다. SQL의 논리적 처리 순서는 FROM·JOIN → WHERE → GROUP BY → SELECT이고(실제 실행 방식은 데이터베이스가 알아서 최적화한다), 이 쿼리에서는 이름을 나중에 붙여도 결과가 같아서 입문자가 따라가기 쉬운 쪽을 택했다. 화면 고지 없음(코드 창의 쿼리 자체는 올바름).
- 구조: 바이블 0-8의 '시도와 실패'를 두 장면으로 나눴다. 장면 3은 시도(SQL이 통함, SELECT·WHERE·GROUP BY·JOIN 첫 등장), 장면 4는 실패(운영 DB 과부하)다. SQL 실행기는 방금 배운 조각을 바로 써 보도록 둘 사이에 두었다. 문제 → 시도·실패 → 개념(장면 5·6) → 해결 순서는 그대로다.
- SQL 실행기의 처리 순서: 그림은 SQL의 '논리적' 처리 순서(FROM → JOIN → WHERE → GROUP BY → SELECT)를 따른다. 실제 데이터베이스는 같은 결과가 나오는 한 순서를 바꾸거나 합쳐서 실행한다(예: 조건을 JOIN보다 먼저 적용). 화면 고지: 도움말 첫 문장 "(실제 데이터베이스는 더 똑똑하게 순서를 바꾸기도 해요)". 장면 3 step 4는 묶은 뒤 이름을 붙이는 모습이지만, 실행기는 논리적 순서대로 JOIN을 먼저 보여 준다(두 순서 모두 이 쿼리에선 결과가 같다).
- SQL 실행기의 해석기는 진짜 SQL 엔진이 아니라 도움말 목록 안팎의 작은 부분만 이해한다. 받아 주는 문법은 표준 SQL(PostgreSQL 기준)과 같은 뜻으로 계산한다: INNER JOIN(짝 없는 행은 빠짐 — 이 데이터엔 없음), `SELECT *`와 JOIN이면 products.product_id 열까지 나옴(7열), 집계와 보통 열을 섞으면 GROUP BY 필요, JOIN 뒤 표 이름 없는 product_id는 모호함 오류, 빈 묶음의 SUM은 NULL·COUNT는 0. 단순화: 별칭(AS)은 쓴 그대로 둔다(PostgreSQL은 따옴표 없는 별칭을 소문자로 바꾼다), `COUNT(열)`은 빈 값이 없는 이 데이터에서 `COUNT(*)`와 같게 센다, 데이터에 연도가 없어 모든 주문과 이야기 속 오늘을 같은 해로 보고 날짜를 비교한다(그래서 `CURRENT_DATE - 366`은 작년 6/3이라 0건, 기록엔 '366일 전(1년 전 6/3)'). 오류 문구 "실제 데이터베이스도 대부분 이 쿼리를 오류로 막아요": PostgreSQL·SQL Server·Oracle 등은 오류를 내고, MySQL은 기본 설정(ONLY_FULL_GROUP_BY)에서 오류를 내지만 설정을 끄면 실행되고, SQLite는 그대로 실행해 임의의 행 값을 보여 주므로 '대부분'으로 썼다.
- 수치: 주문 10건(2001~2010), 가격, 부하 게이지 15%·98%, 결제 번호 #2011~#2013, 어제 9개·29,000원, 전체 15개·49,000원은 모두 이야기 속 가상 설정이다. SQL 실행기의 모든 숫자(행 수, 제외된 주문 번호, 묶음 수, 합계, 결과 값)는 작은 해석기가 공통 데이터에서 직접 계산한 값이다(예: 어제 P1 = 2004의 1개 + 2006의 3개 = 4개, 12,000원). 손으로 적은 결과 숫자는 없다. 해석기 점검: `npx jiti src/chapters/Ch01/sql.check.ts`.

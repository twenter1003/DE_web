### 장면 2. 문제 — 운영 DB 속의 표 [scrub · 3 step]
#### step 1
- 텍스트: 주문이 늘수록 손으로 세는 시간도 늘어요. 주니는 석 리드에게 물어보러 갔고, 석 리드는 CSV가 어디서 왔는지부터 보여 줬어요.
- 대사:
  - 주니(당황): "이거 어떻게 해요?"
  - 석 리드: "운영 DB에 다 있어요. SQL 써 봐요."
- 화면: 석 리드의 책상 앞. 주니 손에 파일 아이콘 '주문내역.csv'. 석 리드 모니터에 원통 모양 노드 '운영 DB'. 원통에서 파일 아이콘으로 실선 화살표, 라벨 '내보내기'.
- 모션: 파일 아이콘에서 화살표가 거꾸로 거슬러 올라가며 그려져 원통 '운영 DB'에 닿고, 닿는 순간 화살표 방향이 '운영 DB → CSV'로 확정된다. (CSV의 출처)

#### step 2
- 텍스트: 데이터베이스(Database, 데이터를 정리해 저장하고 꺼내 쓰게 해 주는 시스템)에는 표가 여러 개 담겨 있어요. 표 하나하나는 테이블(Table, 엑셀 시트 같은 표)이라고 해요. 바구니가 장사하며 매일 쓰는 이 데이터베이스를 '운영 DB'(DB는 데이터베이스의 줄임말)라고 불러요.
- 화면: 원통 '운영 DB'의 뚜껑이 열려 있고, 안에서 테이블 카드 두 장이 위로 나와 있다 — 'orders (주문)', 'products (상품)'.
- 모션: 원통 뚜껑이 열리고 테이블 카드 두 장이 차례로 위로 올라와 나란히 놓인다. (DB 안에 테이블이 들어 있다는 것)

#### step 3
- 텍스트: orders 테이블의 가로 한 줄이 행(Row, 데이터 한 건)이고, 세로 한 줄이 열(Column, 데이터의 항목)이에요. 옆의 products 테이블과는 product_id라는 같은 열을 나눠 갖고 있죠.
- 화면: 왼쪽 orders 표(위 공통 데이터 10행 전부, 캡션 'orders · 6월 1일부터의 주문만 · 일부 열'), 오른쪽 products 표(4행). orders의 2001 행에 가로 강조 띠 + 라벨 '행 = 주문 한 건', qty 열에 세로 강조 띠 + 라벨 '열 = 항목'. 두 표의 product_id 열에 같은 점선 테두리.
- 모션: 가로 띠가 2001 행을 왼쪽에서 오른쪽으로 훑고, 이어서 세로 띠가 qty 열을 위에서 아래로 훑는다. 마지막에 두 표의 product_id 열에 점선 테두리가 동시에 그려진다.

### 장면 3. 시도와 실패 ① — 첫 SQL은 통했어요 [scrub · 4 step]
#### step 1
- 텍스트: SQL(Structured Query Language, 데이터베이스에 데이터를 묻고 다루는 언어)로 쓴 질문 하나를 쿼리(Query, 데이터베이스에 보내는 질문)라고 해요. SELECT는 '보여 줘', FROM은 '어느 표에서'예요.
- 화면: 왼쪽 코드 창
  ```sql
  SELECT *
  FROM orders;
  ```
  오른쪽 orders 표 10행 전부, 모든 행 보통 밝기(캡션 'orders · 6월 1일부터의 주문만'). 코드 창 옆 작은 풀이 '* = 모든 열'.
- 모션: 코드가 한 글자씩 써진다(스크롤 연동). `FROM orders` 타이핑이 끝나는 순간 orders 표 전체 테두리가 한 번 강조된다. (질문이 가리키는 표)

#### step 2
- 텍스트: WHERE는 조건이에요. '주문 날짜가 어제인 것만'이라고 적자 6월 2일 주문 5건만 남았어요.
- 화면: 코드 창
  ```sql
  SELECT *
  FROM orders
  WHERE DATE(ordered_at) = CURRENT_DATE - 1;  -- 어제(6/2)
  ```
  표에서 2004·2005·2006·2007·2008 행은 강조 테두리, 나머지 2001·2002·2003·2009·2010 행은 흐림(불투명도 0.3) + 행 끝 '제외' 라벨. 캡션 '이야기 속 오늘은 6월 3일'. 코드 창 옆 작은 풀이 'CURRENT_DATE - 1 = 오늘의 하루 전 · -- 뒤는 사람이 읽는 메모(주석)'.
- 모션: WHERE 줄이 타이핑되는 동안 ordered_at 열을 위에서 아래로 훑는 선이 내려가며, 6/2가 아닌 행이 지나가는 순서대로 흐려진다.

#### step 3
- 텍스트: GROUP BY는 같은 값끼리 묶어요. 상품별로 묶고 SUM(qty)로 수량을 더하니, 상품마다 숫자 하나로 모였어요.
- 대사: 주니(집중): "어제는 모두 9개! P1이 4개로 제일 많아요."
- 화면: 코드 창
  ```sql
  SELECT product_id, SUM(qty) AS 판매개수
  FROM orders
  WHERE DATE(ordered_at) = CURRENT_DATE - 1
  GROUP BY product_id;
  ```
  결과 표: P1 4 / P2 2 / P3 1 / P4 2. 코드 창 옆 작은 풀이 'SUM = 더하기 · AS = 결과 열에 붙이는 이름'. 결과 표 옆에 주니의 말풍선.
- 모션: 강조된 5행이 product_id별로 미끄러져 모인다(P1 묶음 = 2004·2006). 각 묶음의 qty 칸 숫자가 하나로 합쳐진다(P1: 1 + 3 → 4, 나머지 묶음은 한 행이라 그대로). 합쳐진 뒤 나머지 칸은 사라지고 결과 표 4행만 남는다.

#### step 4
- 텍스트: 그런데 대표님은 P1이 뭔지 모르시겠죠. 조인(JOIN, 두 테이블을 같은 열 값끼리 이어 붙이는 것)으로 products 테이블의 상품 이름을 붙였어요.
- 대사: 윤 대표: "수세미가 제일 잘 나가네요!"
- 화면: 코드 창
  ```sql
  SELECT orders.product_id, name, SUM(qty) AS 판매개수
  FROM orders
  JOIN products ON orders.product_id = products.product_id
  WHERE DATE(ordered_at) = CURRENT_DATE - 1
  GROUP BY orders.product_id, name;
  ```
  결과 표: P1 수세미 4 / P2 칫솔 2 / P3 주방세제 1 / P4 고무장갑 2. 결과 표 오른쪽에 products 표가 붙어 있고, product_id가 같은 칸끼리 연결선 4개(P1↔P1, P2↔P2, P3↔P3, P4↔P4). 주니 어깨 너머로 윤 대표가 결과 표를 들여다보고, 그 위에 윤 대표 말풍선.
- 모션: products 표가 오른쪽에서 들어와 product_id가 같은 칸끼리 선으로 이어지고, 선을 따라 name 값이 결과 표의 product_id 바로 오른쪽 새 열로 옮겨진다.

### 인터랙션: SQL 놀이터
- 위치: 장면 3 다음 (방금 본 SELECT·WHERE·GROUP BY·JOIN을 직접 조합해 보는 자리. 핀 고정 없이 일반 스크롤 흐름 안의 블록)
- 조작:
  - 구성: 위쪽에 조각 선택 3줄, 가운데에 조립된 SQL 코드 창(읽기 전용), 아래에 결과 표와 한 줄 해설. 블록 위 캡션 '연습용 주문 10건 · 이야기 속 오늘은 6월 3일'.
    - [보여줄 것 · SELECT] 전체 주문 / 상품별 개수 / 상품별 매출
    - [기간 · WHERE] 전체 기간 / 어제
    - [상품 이름 · JOIN] 끔 / 켬
  - 처음 상태: 전체 주문 / 전체 기간 / 끔.
  - 각 줄은 라디오 그룹(`<fieldset>` + `<legend>`, 실제 `<input type="radio">`). 키보드: Tab으로 그룹 사이를 이동하고, ←/→(또는 ↑/↓)로 그룹 안에서 선택을 바꾼다. 선택이 바뀌면 바로 결과가 바뀐다.
  - 결과 표는 실제 `<table>`이고 `<caption>`에 '쿼리 결과 · {n}행'. 바뀐 결과는 `aria-live="polite"`로 "결과가 바뀌었어요. 4행. 어제는 모두 9개가 팔렸어요."처럼 행 수 + 한 줄 해설을 읽어 준다.
  - 실제 SQL 엔진은 쓰지 않는다. 12가지 조합의 코드와 결과를 미리 정해 두고 보여 준다.
- 상태별 결과:
  - 코드 조립 규칙
    - 전체 주문 · JOIN 끔: `SELECT *` / `FROM orders`
    - 전체 주문 · JOIN 켬: `SELECT orders.*, products.name` / `FROM orders` / `JOIN products ON orders.product_id = products.product_id`
    - 상품별 개수 · JOIN 끔: `SELECT product_id, SUM(qty) AS 판매개수` / `FROM orders` / `GROUP BY product_id`
    - 상품별 개수 · JOIN 켬: `SELECT orders.product_id, name, SUM(qty) AS 판매개수` / `FROM orders` / `JOIN products ON orders.product_id = products.product_id` / `GROUP BY orders.product_id, name`
    - 상품별 매출: 위 '상품별 개수'와 같고 `SUM(qty) AS 판매개수`만 `SUM(qty * price) AS 매출`로 바뀐다.
    - 기간 '어제': FROM 줄(JOIN이 켜져 있으면 JOIN 줄) 바로 다음, GROUP BY 줄 앞에 `WHERE DATE(ordered_at) = CURRENT_DATE - 1  -- 어제(6/2)` 줄이 끼어든다.
    - 세미콜론(;)은 항상 마지막 줄의 코드 끝에 붙는다. 마지막 줄이 WHERE 줄이면 주석 앞에 붙인다(`WHERE DATE(ordered_at) = CURRENT_DATE - 1;  -- 어제(6/2)`). 주석 뒤에 붙이면 세미콜론까지 주석이 되기 때문이다.
  - 결과 표 (JOIN 켬이면 name 열이 붙는다 — 전체 주문에선 맨 오른쪽, 상품별에선 product_id 바로 오른쪽. SELECT에 적힌 순서와 같다. name 값: P1 수세미, P2 칫솔, P3 주방세제, P4 고무장갑)

    | 보여줄 것 · 기간 | 열 (JOIN 끔 기준) | 행 |
    |---|---|---|
    | 전체 주문 · 전체 기간 | order_id, product_id, qty, price, ordered_at | 공통 데이터 10행 전부 (2001~2010) |
    | 전체 주문 · 어제 | 같음 | 5행: 2004, 2005, 2006, 2007, 2008 |
    | 상품별 개수 · 전체 기간 | product_id, 판매개수 | P1 7 / P2 3 / P3 2 / P4 3 |
    | 상품별 개수 · 어제 | product_id, 판매개수 | P1 4 / P2 2 / P3 1 / P4 2 |
    | 상품별 매출 · 전체 기간 | product_id, 매출 | P1 21,000 / P2 6,000 / P3 10,000 / P4 12,000 |
    | 상품별 매출 · 어제 | product_id, 매출 | P1 12,000 / P2 4,000 / P3 5,000 / P4 8,000 |

  - 결과 행은 product_id(전체 주문은 order_id) 순서로 정렬해 보여 준다.
  - 한 줄 해설 (보여줄 것 · 기간에 따라 바뀜)
    - 전체 주문 · 전체 기간: "주문 10건이 모두 보여요. 아직 거르거나 묶지 않았어요."
    - 전체 주문 · 어제: "WHERE가 6월 2일 주문 5건만 남겼어요."
    - 상품별 개수 · 전체 기간: "GROUP BY가 상품마다 한 줄로 묶었어요. 모두 더하면 15개예요."
    - 상품별 개수 · 어제: "어제는 모두 9개가 팔렸어요. 대표님 질문의 답이에요."
    - 상품별 매출 · 전체 기간: "SUM(qty * price)는 개수 × 개당 가격을 더해요. 모두 더하면 49,000원이에요."
    - 상품별 매출 · 어제: "어제 매출은 모두 29,000원이에요. P1이 12,000원으로 가장 많아요."
    - 뒤에 붙는 문장 — JOIN 끔: "P1~P4가 무슨 상품인지 궁금하면 JOIN을 켜 보세요." / JOIN 켬: "name 열은 products 테이블에서 JOIN으로 붙여 온 거예요."
  - 기본 모드 모션: 바뀐 코드 줄에 강조 밑줄이 0.4초 동안 그어진다. 기간을 '어제'로 바꾸면 조건에 맞지 않는 행이 흐려지며 접히고(0.3초) 남은 행이 위로 붙는다. '상품별'로 바꾸면 같은 product_id 행이 모였다가 숫자 하나로 합쳐진다(0.5초). JOIN을 켜면 name 열이 오른쪽에서 밀려 들어온다(0.3초). 반대 방향 변경은 같은 모션을 거꾸로 재생한다.
- 안내 문구: "조각을 골라 쿼리를 완성해 보세요. 진짜 데이터베이스가 아니라 연습용 주문 10건으로 결과를 보여 줘요." 코드 창 아래 작은 캡션: "※ 날짜를 쓰는 문법은 데이터베이스마다 조금씩 달라요. 결과는 보기 쉽게 정렬했어요(실제로는 ORDER BY로 순서를 정해요)."
- 모션 축소 모드: 애니메이션 없이 코드와 결과 표가 즉시 바뀐다. 바뀐 코드 줄 끝에 '← 바뀐 줄' 글자 표시가 다음 변경 전까지 남는다. 한 줄 해설과 `aria-live` 안내는 기본 모드와 같다.

### 장면 4. 시도와 실패 ② — 운영 DB에 던진 큰 쿼리 [scrub · 3 step]
#### step 1
- 텍스트: 신이 난 주니는 더 큰 질문을 던졌어요. 문을 연 날부터 쌓인 주문 전부에 상품과 고객까지 이어 붙여, 고객별·상품별 매출을 구하는 쿼리였죠.
- 대사:
  - 석 리드: "이걸 운영 DB에 직접요? 음…"
  - 주니(집중): "일단 해 볼게요!"
- 화면: 코드 창
  ```sql
  SELECT customers.name, products.name, SUM(qty * price) AS 매출
  FROM orders
  JOIN products ON orders.product_id = products.product_id
  JOIN customers ON orders.customer_id = customers.customer_id
  GROUP BY customers.name, products.name;  -- 기간 조건 없음: 전체 기간
  ```
  코드 창 옆 작은 풀이 'customers = 고객 테이블'. 코드 창 오른쪽에 게이지 '운영 DB 부하' 15%(초록 구간). 그 아래 결제 카드 자리(비어 있음). 석 리드가 주니 뒤에서 화면을 보고 있다.
- 모션: 긴 쿼리가 한 글자씩 써진다(스크롤 연동). 게이지는 15%에 머문다.

#### step 2
- 텍스트: 쿼리가 쌓인 주문을 전부 훑고 고객·상품 표까지 이어 붙이느라 운영 DB가 바빠졌어요. 그 일에 힘을 쏟는 사이, 손님들의 결제 처리가 느려졌어요.
- 대사: 태오: "결제 페이지가 왜 이렇게 느리죠?"
- 화면: 운영 DB 원통 안의 orders 표 전체를 굵은 빛줄기가 덮고 있다. 게이지 바늘이 빨간 구간 98%, 라벨 '과부하'. 게이지 아래 결제 카드 3장 '결제 #2011 ⏸ 대기', '결제 #2012 ⏸ 대기', '결제 #2013 ⏸ 대기'(회색). 화면 오른쪽 끝에서 태오가 노트북을 들고 다가오고, 그 위에 태오 말풍선. 게이지 아래 작은 캡션: '※ 알아보기 쉽게 부하를 크게 그렸어요. 가게가 작을 땐 티가 덜 나도, 데이터가 쌓일수록 실제로 생기는 일이에요.'
- 모션: 빛줄기가 표를 위에서 아래로 훑을수록(스크롤 진행에 비례) 게이지 바늘이 15% → 98%로 오르고, 결제 카드가 하나씩 ⏸ 상태로 쌓인다. (무거운 분석이 짧은 결제 작업을 밀어낸다)

#### step 3
- 텍스트: 주니가 급히 쿼리를 멈추자 밀렸던 결제가 하나씩 끝났어요. 질문 자체보다, 그 질문을 던진 장소가 문제였죠.
- 대사: 주니(당황): "제, 제 쿼리 때문이었나 봐요!"
- 화면: 태오가 노트북을 들고 주니 책상 옆에 서 있다. 코드 창 위에 '쿼리 중지됨 ✕'. 게이지 15%. 결제 카드 3장 '결제 #2011 ✓ 완료', '#2012 ✓ 완료', '#2013 ✓ 완료'(초록). 주니 표정: 당황.
- 모션: 코드 창의 [중지] 버튼이 눌리면 빛줄기가 사라지고 게이지 바늘이 98% → 15%로 내려가며, 결제 카드의 ⏸가 위에서부터 차례로 ✓로 바뀐다.

### 장면 5. 개념 — 비유: 계산대와 장부 정리 [scrub · 3 step]
#### step 1
- 텍스트: 가게 계산대를 떠올려 보세요. 한 명 계산은 금방 끝나지만, 그 일이 하루 종일 이어져요.
- 화면: 손그림 계산대와 계산원, 줄 선 손님 4명. 앞의 손님 2명 위에 ✓.
- 모션: 손님이 한 명씩 계산대로 다가와 ✓가 붙고 빠져나가면 다음 손님이 앞으로 온다. (짧은 일이 아주 많이, 빠르게)

#### step 2
- 텍스트: 그런데 계산원이 계산대에서 1년치 장부 정리를 시작하면 어떨까요? 장부는 정리되겠지만, 그동안 손님들은 한참을 기다려야 해요.
- 화면: 계산대 위에 두꺼운 장부 '1년치 장부'. 계산원이 장부를 넘기고 있고, 줄 선 손님 4명 위에 모두 ⏸.
- 모션: 장부가 계산대 위에 놓이는 순간 줄의 이동이 멈추고, 손님 위 아이콘이 앞에서부터 차례로 ⏸로 바뀐다.

#### step 3
- 텍스트: 그래서 장부 정리는 보통 뒤쪽 사무실에서 해요. 둘 다 가게 숫자를 다루지만 일의 성격이 달라요.
- 화면: 화면이 둘로 나뉜다. 왼쪽 '계산대' — 줄이 다시 움직이고 손님 위 ✓. 오른쪽 '뒤쪽 사무실' — 책상 위에 '1년치 장부'.
- 모션: 장부가 계산대에서 오른쪽 사무실 책상으로 옮겨지고, 옮겨지는 순간 계산대 줄이 다시 움직이며 ⏸가 ✓로 바뀐다.

### 장면 6. 개념 — 정의와 쇼핑몰 예시: OLTP와 OLAP [scrub · 3 step]
#### step 1
- 텍스트: 계산대 같은 일을 OLTP(Online Transaction Processing, 짧은 읽기·쓰기를 아주 많이, 빠르게 처리하는 방식)라고 해요. 바구니의 운영 DB가 하는 일로, 주문 저장처럼 한 번에 몇 행만 건드려요.
- 화면: 원통 '운영 DB (OLTP)'와 그 안의 orders 표. 짧은 화살표 3개가 각각 행 하나씩만 가리킨다 — '새 주문 저장 · 1행 쓰기', '내 주문 보기 · 1행 읽기', '주문 취소 · 1행 고치기'. 가리킨 행마다 ✓.
- 모션: 짧은 화살표가 번갈아 빠르게 행 하나씩 찍고 지나가며, 찍힌 행에 ✓가 붙는다.

#### step 2
- 텍스트: 장부 정리 같은 일은 OLAP(Online Analytical Processing, 많은 행을 훑어 모으고 계산하는 분석 방식)이에요. '고객별·상품별 전체 매출'처럼 한 번에 아주 많은 행을 읽어요.
- 화면: 같은 orders 표 전체를 빛줄기 하나가 덮고 있다. 표 오른쪽에 '상품별 매출' 막대 4개(수세미·칫솔·주방세제·고무장갑, 숫자 없이 길이만). 라벨 'OLAP'.
- 모션: 빛줄기가 모든 행을 위에서 아래로 한 번 훑은 뒤, 훑은 값들이 오른쪽 막대 4개로 모여 막대가 자란다.

#### step 3
- 텍스트: 같은 DB에서 무거운 OLAP을 돌리면 OLTP가 쓸 힘을 빼앗을 수 있어요. 실제로는 데이터 크기·쿼리 모양·컴퓨터 성능에 따라 영향이 다르지만, 두 일의 성격이 다르다는 점은 같아요.
- 화면: 비교 표.

  |  | OLTP (운영용) | OLAP (분석용) |
  |---|---|---|
  | 바구니 예시 | 주문 저장, 결제 | 고객별·상품별 전체 매출 |
  | 한 번에 다루는 행 | 몇 개 | 아주 많이 |
  | 중요한 것 | 빠른 응답 | 많이 훑는 힘 |

  표 아래 캡션 '※ 단순화한 비교예요.' 표 옆에 작은 게이지 아이콘과 라벨 '같은 DB에서 함께 돌리면 → 부하'.
- 모션: 비교 표가 한 줄씩 채워진다(바구니 예시 → 한 번에 다루는 행 → 중요한 것). 마지막 줄이 채워진 뒤 게이지 아이콘 라벨이 나타난다.

### 장면 7. 해결 — 운영 DB는 계산대에 맡기기 [scrub · 3 step]
#### step 1
- 텍스트: 주니는 당장 지킬 규칙부터 세웠어요. 운영 DB에는 손님이 적은 시간에만, 짧은 기간만 물어보기로요.
- 화면: 주니의 노트북 옆에 포스트잇 3장 — '① 큰 분석은 운영 DB에서 멈추기', '② 손님 적은 시간에만', '③ 짧은 기간만 (어제 하루처럼)'. 노트북 화면 구석의 작은 게이지 '운영 DB 부하 15%'.
- 모션: 포스트잇이 ① → ② → ③ 순서로 한 장씩 붙는다. 게이지는 15%에 머문다.

#### step 2
- 텍스트: 파이프라인 맵에 운영 DB가 생겼어요. CSV는 여기서 뽑아 온 파일이었죠. 노트북에서 운영 DB로 곧장 가는 점선엔 경고가 붙었어요.
- 화면: 파이프라인 맵 — 실선 [쇼핑몰 앱·웹] → [운영 DB (OLTP)] → [CSV 파일] → [주니의 노트북]. 그리고 [주니의 노트북]에서 [운영 DB (OLTP)]로 점선 화살표, 그 위에 빨간 배지(게이지 아이콘 + 글자 '부하 경고'). 노드 수 4.
- 모션: 앱 → CSV 화살표가 가운데에서 끊어지고, 그 틈에 운영 DB 노드가 손그림 선으로 그려지며 끼어든다. 이어서 노트북에서 운영 DB로 점선이 그려지고, 점선 가운데에 '부하 경고' 배지가 붙는다.

#### step 3
- 텍스트: 하지만 규칙만으로는 오래 못 버텨요. 주문도, 대표님의 질문도 매일 늘어날 테니까요.
- 대사:
  - 주니(집중): "분석용은 따로 둬야겠어요."
  - 석 리드: "운영 DB는 안 건드리고요? 어떻게 옮길지가 숙제네요."
- 화면: 석 리드의 책상 앞. 주니가 들고 있는 손그림 종이에 운영 DB 옆으로 연필 점선 상자 '분석용?'이 그려져 있다(장면 속 주니의 메모일 뿐, HUD 파이프라인 맵 노드가 아니다). 주니 표정: 집중.
- 모션: 연필 선이 운영 DB 옆에 점선 상자를 그리고, 상자 안에 '분석용?'이 써진다. (다음 챕터의 질문)

### 한 줄 요약
> SQL로 표에 질문하면 손으로 세지 않아도 되지만, 손님을 받는 운영 DB(OLTP)에서 무거운 분석(OLAP)을 돌리면 서비스가 느려질 수 있어요.

### 퀴즈
- 질문: 주니가 "분석용은 따로 둬야겠어요"라고 결론 내린 가장 큰 이유는 무엇일까요?
- 보기:
  1. 분석 쿼리가 운영 DB의 주문 기록을 고쳐 버릴 수 있어서 — ✕ 해설: 주니가 쓴 SELECT는 데이터를 읽기만 하고 바꾸지 않아요. 기록이 바뀐 게 아니라, 무거운 읽기가 운영 DB를 바쁘게 만든 게 문제였어요.
  2. 많은 행을 훑는 분석(OLAP)이 주문·결제처럼 빨라야 하는 운영 일(OLTP)의 힘을 빼앗기 때문에 — ✓ 해설: 맞아요. 전체 기간을 훑는 큰 쿼리가 운영 DB를 바쁘게 만드는 동안 손님의 결제가 기다려야 했어요. 일의 성격이 다르니 자리를 나누는 거예요.
  3. 운영 DB에는 상품 이름이 없어서 JOIN을 할 수 없기 때문에 — ✕ 해설: products 테이블이 운영 DB 안에 있었고, JOIN으로 이름을 잘 붙였어요.
  4. 운영 DB의 주문 숫자가 CSV보다 부정확해서 — ✕ 해설: CSV는 운영 DB에서 뽑은 사본이에요. 숫자가 틀린 게 아니라, 무거운 질문이 손님의 결제를 늦춘 게 문제였어요.
- 공통 해설: 같은 데이터라도 손님을 받는 일과 장부를 정리하는 일은 성격이 달라요. 그래서 다음 챕터에서 주니는 분석할 데이터를 운영 DB 밖으로 옮기는 방법을 찾아요.

### 카드 정의
- **J — Join(조인)**: 두 테이블에서 같은 열 값을 가진 행끼리 이어 붙여 하나의 결과 표로 합치는 연산
- **O — OLTP vs OLAP**: 짧은 읽기·쓰기를 빠르게 많이 하는 운영용 처리와 많은 행을 훑어 집계하는 분석용 처리의 구분

### 성장 연출
- 카드 획득: J, O 카드가 화면 가운데에서 차례로 뒤집혀 앞면(글자·용어·한 줄 정의·'Ch1')을 보여 준 뒤 HUD로 날아가고, HUD 카드 수가 '2/26 → 4/26'으로 바뀐다. 모션 축소 모드에선 두 카드 앞면을 나란히 보여 주고 카드 수만 바뀐다.

- 맵 변화: HUD 파이프라인 맵 노드 3 → 4. 운영 DB (OLTP) 노드가 app과 csv 사이에 들어가고, 노트북 ⇢ 운영 DB 점선에 '부하 경고' 배지가 남는다(Ch2에서 정리됨). 선의 거칠기는 프롤로그와 거의 같다.

- 주니의 한마디: 주니(집중): "SQL은 재밌는데… 물어볼 곳은 따로 있어야겠어요!"

### 모바일·모션 축소 메모
- 모바일: 코드 창과 표를 세로로 쌓는다(코드 위, 표 아래). 코드는 줄바꿈하지 않고 코드 창 안에서만 가로 스크롤한다(페이지 가로 스크롤 없음). 장면 2 step 3과 장면 3 step 4의 두 표는 세로로 쌓고, JOIN 연결선은 위아래 표의 product_id 칸을 잇는다. SQL 놀이터의 조각 선택 3줄은 각 줄을 화면 폭 꽉 찬 분할 버튼으로 만들고, 6열 결과(전체 주문 · JOIN 켬)는 표 영역 안에서 가로 스크롤한다. 장면 4의 게이지는 코드 창 위에 가로 막대형으로 줄여 놓는다. 장면 5의 계산대·사무실 분할은 위아래로 나눈다. 장면 7 step 2의 맵은 노드를 세로로 배치하고, 점선은 노트북에서 위쪽 운영 DB로 올라간다.
- 모션 축소 모드: 코드 타이핑 대신 각 step의 완성된 코드를 바로 보여 준다. 행 하이라이트·흐림은 그대로 정지 상태로 보여 주되 흐린 행에는 '제외' 글자 라벨을 붙인다. 게이지는 최종 값(15% / 98% '과부하' / 15%)을 숫자와 함께 정지 상태로 표시한다. 결제 카드는 ⏸ 대기 / ✓ 완료 아이콘과 글자로 상태를 구분한다. 장면 3 step 3의 '묶여서 합쳐지는' 과정은 왼쪽에 걸러진 5행, 오른쪽에 결과 4행을 나란히 놓고 사이에 'GROUP BY →' 화살표로 대신한다.

### 정확성 메모
- 화면 속 orders 테이블은 6월 1일부터의 주문만, 일부 열만 보여 준다(프롤로그의 첫날 주문 1001~1005 같은 예전 행은 생략). 어제(6월 2일) 주문은 화면에 모두 있으므로 '어제 9개'는 전체 데이터로도 맞는 답이다. 장면 4의 큰 쿼리는 화면에 나오지 않은 customer_id 열과 customers 테이블을 쓴다. 화면 고지: 장면 2 step 3·장면 3 step 1 표 캡션 'orders · 6월 1일부터의 주문만', 장면 4 step 1 풀이 'customers = 고객 테이블'.
- 날짜 조건 `DATE(ordered_at) = CURRENT_DATE - 1`은 PostgreSQL 방식의 문법이다. 실무에서는 인덱스를 쓰기 좋게 `ordered_at >= … AND ordered_at < …` 범위 조건으로 쓰는 경우가 많지만, 읽기 쉬운 쪽을 택했다. 데이터베이스마다 날짜 함수와 날짜 계산 문법이 다르다. 화면 고지: SQL 놀이터 코드 창 아래 캡션 "※ 날짜를 쓰는 문법은 데이터베이스마다 조금씩 달라요."
- 결과 행 순서: ORDER BY가 없으면 결과 순서는 보장되지 않는다. 화면은 보기 쉽게 product_id·order_id 순으로 정렬했다. 화면 고지: SQL 놀이터 같은 캡션 "결과는 보기 쉽게 정렬했어요(실제로는 ORDER BY로 순서를 정해요)." 장면 3의 결과 표는 고지 없이 같은 정렬을 쓴다(놀이터 고지가 같은 장면 묶음 안에 있음).
- 한국어 별칭(`AS 판매개수`, `AS 매출`)은 학습 편의를 위한 것이다. PostgreSQL에서는 따옴표 없이 쓸 수 있지만 데이터베이스에 따라 따옴표가 필요할 수 있다. 화면 고지 없음(SQL 문법 튜토리얼이 아니므로).
- `SELECT orders.*, products.name`처럼 표 이름을 붙인 열 지정(orders.product_id 등)은 두 표에 같은 이름의 열이 있을 때 헷갈리지 않게 하려는 것이다. 별도 설명 없이 코드에만 쓴다.
- 큰 쿼리로 결제가 느려지는 장면: 실제로는 데이터 크기, 쿼리 모양, 서버 사양, DB 설정에 따라 영향이 크게 다르고, 사용자 100명 규모의 작은 DB라면 티가 안 날 수도 있다. 부하가 결제를 늦추는 원리(CPU·메모리·디스크를 나눠 쓰는 경쟁, 잠금 등)도 '힘을 빼앗는다'로 줄였다. 결제는 완전히 멈추는 게 아니라 느려지는 것이므로 텍스트와 계산대 비유 모두 '기다린다·느려진다'로 썼다. 그래서 장면 4 step 2 텍스트도 '차례를 기다린다' 같은 줄 서기 표현 대신 'DB가 그 일에 힘을 쏟는 사이 결제 처리가 느려졌다'로 썼다(대부분의 DB에서 읽기 쿼리가 쓰기를 줄 세워 막는 것은 아니다). 화면 고지: 장면 4 step 2 캡션 '※ 알아보기 쉽게 부하를 크게 그렸어요…', 장면 6 step 3 텍스트 "실제로는 데이터 크기·쿼리 모양·컴퓨터 성능에 따라 영향이 다르지만…".
- 기간: 바구니는 문을 연 지 얼마 안 된 가게(바이블 0-1)라서 '1년치 주문'은 아직 없다. 큰 쿼리는 '문을 연 날부터 쌓인 전체 주문'으로 썼다. 계산대 비유의 '1년치 장부'는 일반적인 가게 이야기라 그대로 두었다.
- 큰 쿼리의 `GROUP BY customers.name`은 이름이 같은 고객을 하나로 합칠 수 있다(실무라면 customer_id로 묶는다). 신입의 순진한 쿼리라는 설정이고 이 장면의 요점이 아니어서 고지하지 않았다.
- 데이터베이스를 '창고'로 부르지 않았다. Ch4·Ch8에서 웨어하우스(창고)가 분석용 저장소의 비유로 쓰이므로, 운영 DB와 섞이지 않게 하려는 것이다.
- OLTP/OLAP 정의와 비교 표는 단순화한 것이다. 두 일을 함께 처리하도록 설계된 데이터베이스도 있다. 화면 고지: 장면 6 step 3 비교 표 캡션 '※ 단순화한 비교예요.'
- 해결책(손님 적은 시간에만, 짧은 기간만)은 임시방편이다. 운영 DB의 읽기 전용 복제본을 두는 방법 등도 있지만 이 챕터에서는 다루지 않고, Ch2의 분석용 저장소로 이어간다. 화면 고지: 장면 7 step 3 텍스트 "규칙만으로는 오래 못 버텨요."
- "데이터베이스에는 표가 여러 개 담겨 있어요": 관계형 데이터베이스 기준의 설명이다. 표가 아닌 방식으로 저장하는 데이터베이스도 있다. 화면 고지 없음(이 페이지가 다루는 운영 DB·웨어하우스가 표 중심이라 입문 단계에서 오해를 만들지 않음).
- 맵: 프롤로그의 app → csv 실선을 app → oltp → csv로 다시 그렸다. CSV가 운영 DB에서 뽑은 사본이라는 사실(장면 2 step 1)과 Ch2에서 야간 ETL이 수동 내보내기(csv)를 대체하는 흐름에 맞춘 것이다. 노트북 ⇢ 운영 DB 점선은 바이블 0-7의 'Ch1 직접 쿼리(점선, 부하 경고)'를 따른다.
- 한 주문 = 한 상품: 실제로는 주문 한 건에 여러 상품이 담기므로 주문 항목 테이블을 따로 두는 경우가 많다. JOIN·GROUP BY를 보여 주는 데 집중하려고 orders 한 행에 상품 하나만 두었다. 주문 항목 같은 '사건' 테이블은 Ch4 팩트 테이블에서 다시 다룬다. 화면 고지 없음.
- JOIN 장면의 순서: 장면 3 step 4는 이미 묶인 결과 4행에 상품 이름을 붙이는 모습으로 그렸다. 실제로 데이터베이스는 코드에 적힌 대로 JOIN을 먼저 하고 WHERE·GROUP BY를 하지만, 이 쿼리에서는 결과가 같아서 입문자가 따라가기 쉬운 쪽을 택했다. 화면 고지 없음(코드 창에는 실제 순서대로 적혀 있음).
- 구조: 바이블 0-8의 '시도와 실패'를 두 장면으로 나눴다. 장면 3은 시도(SQL이 통함, SELECT·WHERE·GROUP BY·JOIN 첫 등장), 장면 4는 실패(운영 DB 과부하)다. SQL 놀이터는 방금 배운 조각을 바로 써 보도록 둘 사이에 두었다. 문제 → 시도·실패 → 개념(장면 5·6) → 해결 순서는 그대로다.
- 수치: 주문 10건(2001~2010), 가격, 부하 게이지 15%·98%, 결제 번호 #2011~#2013, 어제 9개·29,000원, 전체 15개·49,000원은 모두 이야기 속 가상 설정이다. 놀이터의 모든 결과 숫자는 위 공통 데이터에서 직접 계산한 값이다(예: 어제 P1 = 2004의 1개 + 2006의 3개 = 4개, 12,000원).

## Ch4. 매출이 두 개예요 — 웨어하우스와 데이터 모델링

- 레벨: Lv2→3 / 회사 규모: 사용자 1만 명 / 분량: 약 3분
- 등장인물: 주니, 윤 대표, 소라(첫 등장), 민재(첫 등장), 다온(첫 등장 · 이번 챕터에 합류)
- 획득 카드: F, N, W
- 맵 변화: warehouse 라벨 '분석용 DB' → '데이터 웨어하우스', + model(모델링·지표 정의 (dbt 등)), bi 라벨 '아침 리포트' → 'BI 대시보드' (노드 7 → 8). 실선 warehouse → bi가 warehouse → model → bi로 바뀜
- 역량 변화: sql +20, pipeline +5, ops +5, design +10, lead +8

### 장면 1. 오프닝 (스크롤 연동 아님)
- 화면: 화면 왼쪽 1/3은 주니의 책상(Lv2 환경). 노트북 자리는 비어 있고, 외장 모니터에 작은 DAG(노드 5개, 모두 ✓ — Ch3 끝과 같은 화면), 머그컵, 포스트잇 두 장. 오른쪽 2/3은 회의실. 긴 테이블에 윤 대표, 소라, 민재, 노트북을 펼친 주니. 소라와 민재 앞에 각자 숫자 카드가 서 있다: 소라 "120,000,000원", 민재 "98,000,000원". 두 카드 사이 테이블 위에 손글씨 "≠". 두 카드 아래 작은 회색 글씨 "가상 수치". 동료 방문: 이 챕터에서 주니 책상에 오는 동료는 한 번에 1명(장면 3의 소라, 다온).
- 대사:
  - 소라: "지난달 매출 1억 2천! 역대 최고예요!"
  - 민재: "아니요, 9천 8백이에요."
  - 윤 대표: "매출이 두 개예요? 그래서 얼마예요?"
  - 주니(당황): "둘 다 같은 데이터에서 나왔는데…"

### 장면 2. 문제 — 같은 이름, 다른 계산 [scrub · 3 step]
#### step 1
- 텍스트: 같은 달, 같은 '매출'인데 숫자가 두 개예요. 둘 다 각자의 쿼리로 계산했어요. 누가 틀린 걸까요?
- 화면: 가운데에 '분석용 DB' 노드 하나. 노드에서 왼쪽 아래로 화살표 → 소라의 숫자 카드 "매출 120,000,000원"(카드 위 라벨 '소라의 쿼리'), 오른쪽 아래로 화살표 → 민재의 카드 "매출 98,000,000원"(라벨 '민재의 쿼리'). 두 카드 사이에 손글씨 "≠". 카드 아래 "가상 수치".
- 모션: 분석용 DB 노드에서 입자가 두 갈래로 흘러나가 양쪽 카드에 닿고, 닿는 순간 각 카드 숫자가 0에서 최종값까지 카운트업된다(같은 원본이 두 계산으로 갈라진다는 것). 마지막에 가운데 "≠"가 선으로 그려진다.

#### step 2
- 텍스트: 주문 네 건으로 따라가 볼게요. 소라는 할인 전 금액에 배송비를 더하고, 취소·환불된 주문도 셌어요.
- 대사: 소라: "주문이 들어왔으면 매출이죠!"
- 화면: 표 하나(5열 × 4행), 표 위 작은 라벨 "주문 4건만 떼어 본 예시".

  | 주문 | 상품 금액 | 배송비 | 할인 | 상태 |
  |---|---|---|---|---|
  | #101 | 30,000 | 3,000 | 3,000 | 완료 |
  | #102 | 20,000 | 3,000 | 0 | 취소 |
  | #103 | 50,000 | 0 | 5,000 | 완료 |
  | #104 | 10,000 | 3,000 | 0 | 환불 |

  '소라의 규칙' 상태: 4행 전부 강조색 배경, '상품 금액'·'배송비' 열 머리글 강조, '할인' 열은 회색(적용 안 함). 표 아래 합계 칸 "소라의 매출 = 119,000원", 옆에 규칙 한 줄 "할인 전 · 배송비 포함 · 취소·환불 포함".
- 모션: 행 4개가 위에서부터 한 줄씩 하이라이트되고, 각 행의 상품 금액+배송비 값(33,000 / 23,000 / 50,000 / 13,000)이 입자가 되어 표 아래 합계 칸으로 모인다. 합계가 0 → 119,000원으로 쌓인다.

#### step 3
- 텍스트: 민재는 취소·환불 주문과 할인, 배송비를 모두 뺐어요. 둘 다 계산은 맞아요. 다른 건 '무엇을 매출로 셀지'예요.
- 대사: 민재: "취소된 주문은 돈이 안 들어왔잖아요."
- 화면: 같은 표. '민재의 규칙' 상태: #102·#104 행에 취소선 + ✕ 아이콘 + "제외" 라벨, '배송비' 열 회색. #101 금액 칸에 "30,000 − 3,000 = 27,000", #103에 "50,000 − 5,000 = 45,000". 표 아래 합계 칸 두 개를 나란히: "소라의 매출 119,000원 · 할인 전 · 배송비 포함 · 취소·환불 포함" / "민재의 매출 72,000원 · 할인 후 · 배송비 제외 · 취소·환불 제외". 두 합계 사이에 "계산 ✓ / 정의가 다름".
- 모션: 소라의 하이라이트가 빠지고, #102·#104 행에 취소선이 왼쪽에서 오른쪽으로 그어진다. 이어서 배송비 열이 회색으로 바래고, 남은 두 행의 할인 값이 금액 칸으로 이동해 빠지며 27,000·45,000으로 바뀐다. 합계 0 → 72,000원.

### 장면 3. 시도와 실패 — 쿼리가 하나씩 늘어나요 [scrub · 3 step]
#### step 1
- 텍스트: 주니의 해결책은 간단했어요. 기준마다 쿼리를 하나씩 만들어 주는 거예요.
- 대사: 주니(뿌듯): "기준별로 하나씩 만들면 돼요."
- 화면: 주니 책상의 외장 모니터를 확대한 화면. 위에 '분석용 DB' 노드, 아래에 쿼리 파일 노드 2개: "매출_마케팅 → 1억 2천", "매출_재무 → 9천 8백". 각 파일 옆에 요청자 이름표(소라 ✓, 민재 ✓). 모니터 옆에 소라가 서 있다(동료 1명).
- 모션: 분석용 DB에서 아래로 화살표 두 개가 그려지고 끝에 파일 노드가 하나씩 생긴다. 파일마다 ✓가 찍힌다.

#### step 2
- 텍스트: 요청은 계속 왔어요. '매출' 쿼리가 다섯 개, 결과도 다섯 가지가 됐죠. 새로 합류한 분석가 다온은 어느 걸 믿을지 몰라요.
- 대사: 다온: "저는 어떤 '매출'을 쓰면 되죠?"
- 화면: 쿼리 파일 노드 5개가 줄 맞춤 없이 흩어져 있다: "매출_마케팅 → 1억 2천", "매출_재무 → 9천 8백", "매출_광고 → 1억 1천 3백", "매출_대표보고 → 1억 4백", "매출_고객센터 → 1억 7백"(모두 지난달 기준 · 가상 수치). 파일 사이에 연결선 없음. 오른쪽에 다온(이름표 "다온 · 데이터 분석가")이 파일 더미를 보며 서 있고, 머리 위 말풍선에 "?". 소라는 화면에서 빠진다(동료 1명 유지).
- 모션: 파일 노드가 하나씩 3개 더 그려진다(2 → 5). 새 파일이 생길 때마다 결과 숫자가 서로 다른 값으로 찍힌다. 마지막에 다온이 오른쪽에서 들어온다.

#### step 3
- 텍스트: 게다가 데이터가 쌓이면서 쿼리가 점점 느려졌어요. 바구니의 분석용 DB는 운영 DB와 같은 종류라, 한 건씩 다루기엔 좋아도 큰 집계엔 약했거든요.
- 대사: 주니(당황): "쿼리를 늘릴수록 숫자도, 기다림도 늘어나요…"
- 화면: 파일 5개 모두 ⏸ 아이콘 + "집계 중" 라벨. 분석용 DB 노드 옆에 게이지 '집계 대기'가 빨간 구간에 있고, 바늘 옆에 "느림" 텍스트. 모니터 옆의 주니는 당황 표정.
- 모션: 5개 파일에서 동시에 화살표가 분석용 DB로 들어가고, 게이지 바늘이 초록 구간에서 빨간 구간으로 올라간다. 바늘이 빨간 구간에 닿으면 파일 아이콘이 ✓ → ⏸로 바뀐다.

### 장면 4. 개념 — 잘 정리된 도서관, 데이터 웨어하우스 [scrub · 4 step]
#### step 1
- 텍스트: 책이 바닥에 쌓여 있으면 한 권 찾기도 힘들어요. 도서관은 주제별 서가와 색인으로 바로 찾게 해 줘요.
- 화면: 좌우 분할. 왼쪽 '방바닥': 비스듬히 쌓인 책 더미(책 등에 '주문', '상품', '고객', '매출' 같은 글자가 뒤섞여 있음). 오른쪽 '도서관': 서가 3개(라벨 '주문', '상품', '고객')에 책이 반듯하게 꽂혀 있고, 앞에 색인 카드 상자. 맨 앞 카드에 "매출 → '주문' 서가, 3번 칸".
- 모션: 왼쪽 더미의 책들이 한 권씩 오른쪽으로 이동해 책 등 글자에 맞는 서가에 꽂힌다. 다 꽂히면 색인 카드 상자에서 카드 한 장이 올라온다(정리 + 찾는 길).

#### step 2
- 텍스트: 데이터의 도서관이 데이터 웨어하우스(Data Warehouse, 분석을 위해 정리된 데이터를 모아 두는 저장소)예요. 분석용 DB가 운영 DB의 표를 옮겨 둔 곳이라면, 웨어하우스는 분석하기 좋은 모양으로 다시 정리해 둔 곳이에요.
- 화면: 큰 노드 '데이터 웨어하우스' 안에 표 아이콘 3개(라벨 '주문', '상품', '고객'). 노드 옆 대응표 2줄: "서가 → 주제별로 정리된 표", "색인 → 무엇이 어디 있고 무슨 뜻인지 적은 정의".
- 모션: 도서관 그림의 서가 3개가 같은 자리에서 표 아이콘 3개로 모양이 바뀌고(morph), 서가를 감싸던 건물 윤곽이 '데이터 웨어하우스' 노드 테두리로 다시 그려진다. 대응표 화살표 2개가 차례로 그려진다.

#### step 3
- 텍스트: 웨어하우스가 큰 집계에 빠른 비결 하나는 저장 방식이에요. 바구니의 분석용 DB는 운영 DB와 같은 종류라 행 기반 저장(Row-oriented storage, 한 건의 값을 한데 붙여 저장하는 방식)을 써요. 한 건을 넣고 꺼내기엔 좋지만, 상품과 금액만 필요해도 주문을 통째로 읽어요.
- 화면: 위쪽에 질문 라벨 "상품별 매출은?". 그 아래 저장 모습: 가로로 긴 블록 6개(행 하나 = 블록 하나), 블록마다 칸 5개.

  | 주문 | 날짜 | 고객 | 상품 | 금액 |
  |---|---|---|---|---|
  | 201 | 10-01 | C1 | 수건 | 12,000 |
  | 202 | 10-01 | C2 | 머그컵 | 8,000 |
  | 203 | 10-02 | C1 | 수건 | 12,000 |
  | 204 | 10-02 | C3 | 칫솔 | 4,000 |
  | 205 | 10-03 | C2 | 머그컵 | 8,000 |
  | 206 | 10-03 | C4 | 수건 | 12,000 |

  6개 블록 전체에 '읽음' 테두리. 상품·금액 칸은 진하게, 주문·날짜·고객 칸은 읽었지만 버려져 흐리게. 오른쪽 위 카운터 "읽은 칸: 30 / 30".
- 모션: 읽기 커서가 블록 1부터 6까지 한 줄씩 왼쪽 → 오른쪽으로 모든 칸을 지나간다. 카운터가 0 → 30으로 오르고, 커서가 지나간 주문·날짜·고객 칸은 바로 흐려진다(읽고 버린 칸).

#### step 4
- 텍스트: 많은 웨어하우스는 열 기반 저장(Column-oriented storage, 같은 열의 값끼리 모아 저장하는 방식)을 써요. 필요한 열만 읽고, 같은 종류의 값끼리 모여 있어 압축도 잘 돼요. 실제로는 더 복잡하지만 핵심은 이거예요.
- 화면: 같은 데이터가 세로 블록 5개(열 하나 = 블록 하나: 주문 / 날짜 / 고객 / 상품 / 금액)로 저장된 모습. '상품'·'금액' 블록만 강조색, 나머지 3개는 회색. 카운터 "읽은 칸: 12 / 30". '상품' 블록 옆 작은 사전 상자 "수건=1, 머그컵=2, 칫솔=3"이 있고, 블록 안 값은 "1 2 1 3 2 1"로 짧아져 있다(압축 표시). 오른쪽 결과 표: "수건 36,000 / 머그컵 16,000 / 칫솔 4,000". 화면 구석 배지 "단순화한 그림".
- 모션: 가로 블록 6개가 칸 단위로 흩어졌다가 같은 열끼리 세로로 다시 쌓인다(행 → 열 재배열). 이어서 강조색 세로 빛줄기가 '상품'·'금액' 블록만 위에서 아래로 훑고, 카운터가 0 → 12로 오른다. 마지막에 상품 블록의 단어들이 숫자 코드로 바뀌며 블록이 짧아지고(압축), 결과 표가 채워진다.

### 장면 5. 개념 — 나눌까, 합칠까: 스타 스키마 [scrub · 4 step]
#### step 1
- 텍스트: 운영 DB는 보통 정규화(Normalization, 중복을 줄이려고 테이블을 나누는 것)를 해요. 상품 이름은 한 번만 적으니, 바뀌어도 한 곳만 고치면 돼요.
- 화면: 작은 표 3개가 가로로 놓이고 키 연결선으로 이어져 있다.
  - 주문 항목(주문, 상품번호, 수량, 금액): 201 · P1 · 1 · 12,000 / 202 · P2 · 1 · 8,000 / 203 · P1 · 1 · 12,000 / 204 · P3 · 1 · 4,000
  - 상품(상품번호, 이름, 분류번호): P1 · 수건 · K1 / P2 · 머그컵 · K2 / P3 · 칫솔 · K1
  - 분류(분류번호, 분류명): K1 · 욕실 / K2 · 주방
  
  상품 표의 '수건' 칸에 강조 테두리 + 라벨 "여기 한 번만". 세 표 위에 흐린 축소판 '나누기 전'(주문마다 상품 이름·분류명이 다 들어 있던 넓은 표를 줄인 그림. 읽을 크기가 아니므로 칸 글자는 막대로 대신하고, 반복된 '수건' 2칸·'욕실' 3칸 자리에 회색 밑줄)이 있고, 축소판에서 세 표로 내려오는 화살표.
- 모션: 넓은 표 하나(주문 4행에 상품 이름·분류명이 한 줄씩 다 들어 있는 표, '수건'이 두 번·'욕실'이 세 번 반복됨)에 점선 가위선이 그어지고, 세 조각으로 나뉘어 벌어진다. 조각 사이에 키 연결선(P1 ↔ P1, K1 ↔ K1)이 그려지고, 반복되던 '수건' 두 칸이 상품 표의 한 칸으로 합쳐진다. 원래의 넓은 표는 위쪽으로 줄어들어 흐린 '나누기 전' 축소판으로 남는다.

#### step 2
- 텍스트: 분석할 땐 조인이 여러 번 필요해 번거로워요. 그래서 자주 같이 보는 정보는 비정규화(Denormalization, 분석 편의를 위해 일부러 합쳐 두는 것)해 둬요. 같은 분류명이 여러 번 적히는 대신, 조인이 줄어요.
- 화면: 왼쪽: 주문 항목 —JOIN— 상품 —JOIN— 분류, 연결선마다 "JOIN" 라벨(2개). 오른쪽: 합쳐진 상품 표(상품번호, 이름, 분류명): P1 · 수건 · 욕실 / P2 · 머그컵 · 주방 / P3 · 칫솔 · 욕실. '욕실'이 두 번 나오는 칸에 작은 라벨 "중복이 조금 생김", 연결선 위에 "JOIN 2 → 1".
- 모션: 분류 표가 상품 표 오른쪽으로 미끄러져 붙으며 '분류명' 열 하나가 된다. 그 사이의 JOIN 라벨 하나가 지워지고 카운터가 "JOIN 2 → 1"로 바뀐다.

#### step 3
- 텍스트: 웨어하우스는 흔히 팩트 테이블(Fact table, 측정할 사건과 숫자를 담는 테이블)을 중심에 둬요. 주문 항목 하나가 한 행이고, 수량·금액과 날짜·상품·고객을 가리키는 번호(키)를 가져요.
- 화면: 가운데 '주문 항목 팩트' 표: 열 = 날짜 키, 상품 키, 고객 키, 수량, 금액. 샘플 3행: 10-01 · P1 · C1 · 1 · 12,000 / 10-01 · P2 · C2 · 1 · 8,000 / 10-02 · P1 · C1 · 1 · 12,000. 수량·금액 열 위에 강조색 라벨 "측정값", 키 열 3개 위에 테두리만 있는 라벨 "키". 키 열마다 바깥으로 짧은 화살표(위, 왼쪽 아래, 오른쪽 아래)가 뻗어 있고 끝은 비어 있다.
- 모션: 팩트 표가 가운데에 그려진 뒤, 키 열 3개에서 화살표가 한 방향씩 바깥으로 뻗어 나간다. 화살표 끝은 아직 비어 있다(무언가를 가리킨다는 것).

#### step 4
- 텍스트: 키가 가리키는 곳엔 디멘션 테이블(Dimension table, 사건을 설명하는 속성을 담는 테이블)이 있어요. 이 모양이 스타 스키마(Star schema, 팩트를 디멘션 여럿이 별처럼 둘러싼 구조)예요. 분류별 월 매출도 팩트에서 선 두 개만 따라가면 돼요.
- 화면: 가운데 팩트 표, 위에 '날짜' 디멘션(날짜 키, 연, 월, 요일), 왼쪽 아래 '상품' 디멘션(상품 키, 이름, 분류 — 분류 칸 옆 작은 라벨 "step 2에서 합쳐 둠"), 오른쪽 아래 '고객' 디멘션(고객 키, 지역, 가입 월). 팩트에서 세 디멘션으로 뻗은 선이 별 모양을 이룬다. 위쪽 질문 라벨 "분류별 월 매출은?", 팩트–상품, 팩트–날짜 두 선만 강조색. 오른쪽 결과 미니표 "10월 · 욕실 24,000원 / 주방 8,000원"과 아래 작은 글씨 "팩트 3행만 더한 예시"(화면의 팩트 3행 = 욕실 12,000 + 12,000, 주방 8,000).
- 모션: 세 디멘션 표가 step 3 화살표 끝에서 하나씩 그려진다(날짜 → 상품 → 고객). 질문 라벨이 뜨면 필요한 두 선만 강조색으로 바뀌고, 그 선을 따라 입자가 팩트로 모였다가, 팩트 제목·'측정값' 라벨 오른쪽으로 올라가 결과 자리에 닿는다. 입자가 사라진 뒤 결과 미니표가 나타난다(입자가 라벨·캡션 위를 지나지 않게).

### 장면 6. 해결 — 이름 붙인 정의는 한곳에 [scrub · 4 step]
#### step 1
- 텍스트: 주니는 쿼리를 늘리는 대신 데이터를 웨어하우스에 스타 스키마로 정리하고, '총매출'과 '순매출'을 한 번씩만 정의했어요. 이게 SSOT(Single Source of Truth, 지표 정의 같은 기준을 한곳에서 관리하는 원칙)예요.
- 대사: 주니(집중): "정의는 한곳에 두고, 모두 그걸 쓰면 돼요."
- 화면: 가운데 '지표 정의' 상자. 안에 정의 카드 2장.
  - 총매출: 주문된 금액 그대로의 합계 · 할인 전 · 배송비 포함 · 취소·환불 포함 · 담당 소라
  - 순매출: 상품 판매로 실제 들어온 금액 합계 · 할인 후 · 배송비 제외 · 취소·환불 제외 · 담당 민재
  
  상자 위 카운터 "매출 쿼리 5 → 지표 정의 2". 상자 밑받침에 작은 스타 스키마 그림(팩트 1 + 디멘션 3)과 라벨 "데이터 웨어하우스" — 정의가 정리된 데이터 위에 놓여 있다는 것. 상자 아래 작은 글씨 "실제 회계의 총매출은 보통 취소된 주문을 빼요. 여기서는 바구니가 내부에서 정한 정의예요."
- 모션: 장면 3에서 흩어져 있던 쿼리 파일 5개가 가운데로 모여 겹쳐지고, 두 장의 정의 카드로 접혀 정리된다. 카운터가 5 → 2로 바뀐다.

#### step 2
- 텍스트: 정의는 dbt(data build tool, SQL로 쓴 변환을 파일로 관리하고 실행하는 도구) 같은 도구를 써서 코드 파일로 만들어요. 이 파일을 Git 같은 버전 관리 도구(Version control system, 파일이 바뀐 기록을 쌓아 두는 도구)에 두면, 누가 언제 바꿨는지 보이고 바꾸기 전에 함께 검토할 수 있어요.
- 화면: 정의 카드 2장이 파일 탭 모양으로 바뀌어 있다: "총매출.sql", "순매출.sql". '순매출.sql' 아래 변경 기록 3줄: "민재 · 배송비 제외 조건 확인", "주니 · 취소·환불 제외 추가", "주니 · 처음 작성". 맨 위 줄 옆에 "검토 ✓".
- 모션: 정의 카드가 파일 탭으로 모양을 바꾼 뒤, 변경 기록이 아래에서 위로 한 줄씩 쌓인다(오래된 것이 아래). 마지막 줄에 "검토 ✓"가 찍힌다.

#### step 3
- 텍스트: 맵에서 분석용 DB는 데이터 웨어하우스가 되고, 모델링·지표 정의 노드가 생겨요. 아침 리포트는 BI 대시보드(Business Intelligence dashboard, 지표를 그래프·표로 한눈에 보는 화면)가 돼요.
- 화면: 파이프라인 맵 8노드: app(쇼핑몰 앱·웹) → oltp(운영 DB (OLTP)) → etl(야간 ETL 배치) → warehouse(데이터 웨어하우스) → model(모델링·지표 정의 (dbt 등)) → bi(BI 대시보드). orch(오케스트레이터 (Airflow 등)) ⇢ etl 점선 제어 화살표와 orch ⇢ alert(실패 알림) 점선은 Ch3과 같다. model 노드에 '새 노드' 강조 테두리. warehouse 옆 '집계 대기' 게이지는 초록 구간 ✓. 맵 아래 작은 캡션: "실제로는 지표 계산도 웨어하우스 안에서 돌아가요. 맵에선 단계를 나눠 그렸어요."
- 모션: warehouse 라벨의 '분석용 DB' 글자가 지워지고 '데이터 웨어하우스'가 써지며 박스 테두리가 한 번 다시 그려진다. warehouse → bi 화살표가 가운데서 끊기고, 그 자리에 model 노드가 그려진 뒤 warehouse → model → bi 두 화살표로 다시 이어진다. 이어서 bi 라벨이 '아침 리포트' → 'BI 대시보드'로 바뀐다.

#### step 4
- 텍스트: 다시 열린 회의, 집계는 금방 끝나고 두 숫자엔 이름표가 붙었어요. 둘 다 맞았고, 정의가 달랐을 뿐이에요.
- 대사:
  - 소라: "광고 성과는 총매출로 볼게요."
  - 민재: "장부는 순매출로요."
- 화면: 오프닝과 같은 회의실. 벽 스크린에 BI 대시보드 타일 2개: "총매출 120,000,000원 ✓ · 정의 보기", "순매출 98,000,000원 ✓ · 정의 보기"(가상 수치). 테이블 위에는 숫자 카드도 "≠"도 없다 — 두 숫자는 이름 붙은 타일로만 남아 있다.
- 모션: 오프닝의 두 숫자 카드가 스크린의 타일 자리로 이동하고, 각 카드에 이름표('총매출', '순매출')가 붙는다. 그 사이의 "≠"가 지워진다.

### 한 줄 요약
> 데이터는 웨어하우스에 분석하기 좋은 모양으로 정리하고, '매출' 같은 지표는 이름을 붙여 한곳에서 정의한 뒤 모두가 같이 써요.

### 퀴즈
- 질문: 회의에서 '매출'이 두 개 나온 문제를 다시 겪지 않으려면, 무엇이 가장 필요했을까요?
- 보기:
  1. 더 빠른 저장소로 옮겨 쿼리를 빨리 돌린다 — ✕ 해설: 속도는 기다리는 시간을 줄여 줄 뿐이에요. 정의가 다르면 아무리 빨리 계산해도 숫자는 여전히 두 개예요.
  2. 팀마다 원하는 기준의 매출 쿼리를 하나씩 더 만들어 준다 — ✕ 해설: 주니가 처음 한 시도예요. 쿼리가 늘수록 '어느 매출이 맞나'라는 질문도 함께 늘어나요.
  3. '총매출'과 '순매출'처럼 지표에 이름을 붙여 한곳에서 정의하고, 모두 그 정의를 쓴다 — ✓ 해설: 숫자가 둘이었던 이유는 계산 실수가 아니라 정의 차이였어요. 정의를 한곳에 두면 같은 이름은 언제나 같은 뜻이 돼요.
  4. 둘 중 틀린 숫자를 찾아 지운다 — ✕ 해설: 둘 다 계산은 맞았어요. 한쪽을 지우면 그 숫자가 꼭 필요한 팀이 지표를 잃어요.
- 공통 해설: 웨어하우스와 스타 스키마는 데이터를 분석하기 좋게 정리하고, SSOT는 그 위에서 '무엇을 셀지'를 하나로 맞춰요. 정리된 데이터는 답을 빠르게, 한곳의 정의는 답을 하나의 뜻으로 만들어 줘요.

### 카드 정의
- **F — Fact table(팩트 테이블)**: 주문 항목처럼 측정할 사건을 한 행씩 담고, 수량·금액 같은 측정값과 디멘션을 가리키는 키를 가진 중심 테이블
- **N — Normalization(정규화)**: 같은 정보가 여러 곳에 반복해 적히지 않도록 테이블을 나눠, 중복을 줄이고 한 곳만 고치면 되게 하는 설계 방식
- **W — Warehouse(데이터 웨어하우스)**: 여러 시스템에서 모은 데이터를 분석하기 좋은 모양으로 정리해, 큰 집계를 빠르게 하도록 만든 분석 전용 저장소

### 성장 연출
- 카드 획득: F → N → W 순서로 카드 3장이 한 장씩 뒤집혀 앞면(글자 + 용어 + 한 줄 정의 + "Ch4")을 보여 준 뒤 HUD의 도감 아이콘으로 들어간다. 도감 카운터 +3.
- 역량 변화: 레이더 차트에서 sql +20, pipeline +5, ops +5, design +10, lead +8 축이 각각 늘어난다. 늘어난 축 끝에 "+20"처럼 수치 라벨. 차트 아래 한 줄 "레이더는 학습을 돕는 장치예요. 실제 역량 평가가 아니에요."
- 맵 변화: 미니 맵에서 warehouse 라벨이 '데이터 웨어하우스'로, bi 라벨이 'BI 대시보드'로 바뀌고 model 노드가 반짝임 없이 테두리만 한 번 그려진다(노드 7 → 8).
- 레벨업: Lv2 주니어 → Lv3 미드레벨. HUD의 레벨 배지가 "Lv3 미드레벨"로 바뀐다. 주니의 책상이 바뀐다: 외장 모니터 옆에 모니터가 하나 더 생겨 듀얼 모니터가 되고(왼쪽: 스타 스키마 다이어그램, 오른쪽: 맵), 책상 뒤에 화이트보드가 세워진다. 화이트보드에는 오늘 그린 스타 스키마 스케치(팩트 하나 + 디멘션 셋). 다온이 노트북을 들고 책상으로 와서 말풍선을 띄운다: "주니, 순매출을 주 단위로 보려면요?" 그 뒤에서 민재가 서류철을 들고 차례를 기다린다(동료 2명 — Lv3 환경).
- 주니의 한마디(뿌듯): "순매출 정의를 쓰면 되는데, 늦게 들어오는 환불은 조심해야 해요."

### 모바일·모션 축소 메모
- 모바일: 오프닝은 책상(위) → 회의실(아래) 세로 배치. 장면 2의 5열 표는 '상품 금액'을 '상품가'로 줄여 한 화면에 맞추고, 합계 칸 두 개는 세로로 쌓는다. 장면 4의 행/열 저장 블록은 블록 크기를 줄여 같은 6×5 칸을 유지한다(칸 수 비교가 핵심이라 칸을 빼지 않는다). 장면 5 step 4의 스타 스키마는 팩트를 가운데 위에, 디멘션 3개를 아래 한 줄로 두고 선으로 잇는다.
- 모션 축소: 모든 step은 '화면'에 적힌 최종 상태를 정지 그림으로 보여 준다. 카운트업·합계 숫자는 최종값으로 바로 표시하고, 행 → 열 재배열(장면 4 step 4)은 왼쪽 '행 저장' 그림과 오른쪽 '열 저장' 그림을 나란히 놓아 대신한다. 빛줄기는 강조색 테두리로 대신한다.
- 색만으로 구분하지 않기: 제외 행은 취소선 + ✕ + "제외" 텍스트, 측정값/키는 라벨 텍스트, 게이지는 "느림"/✓ 텍스트를 함께 쓴다.

### 정확성 메모
- 시점: 회의는 11월 초, '지난달'은 10월이다. 장면 4~5 예시 표의 날짜(10-01~10-03)도 10월이다. Ch5의 로그 날짜는 이보다 뒤(이듬해 3월)로 맞췄다.
- 매출 1억 2천·9천 8백, 쿼리 5개의 결과값(모두 지난달 한 달 기준), 주문 표의 금액은 모두 바구니 안의 가상 수치다. 화면 고지: 오프닝·장면 2 step 1·장면 3 step 2·장면 6 step 4의 "가상 수치" 라벨, 장면 2 step 2의 "주문 4건만 떼어 본 예시".
- 총매출·순매출의 범위(할인·배송비·취소·환불 처리)는 바구니가 내부에서 정한 정의로 설정했다. 실제 회계 기준과 회사별 정의는 더 복잡하고 다를 수 있다. 화면 고지: 장면 6 step 1 정의 상자 아래 "실제 회계의 총매출은 보통 취소된 주문을 빼요. 여기서는 바구니가 내부에서 정한 정의예요."
- 4건 예시의 비율(119,000 : 72,000)은 월 전체 비율(1억 2천 : 9천 8백)과 맞지 않는다. 일부 건만 떼어 본 예시라 의도적으로 맞추지 않았다.
- 분석용 DB를 행 기반 DB로 설정했다(Ch2의 분석용 DB를 운영 DB와 같은 종류의 DB로 가정). 이 가정은 장면 3 step 3과 장면 4 step 3 본문에 "바구니의 분석용 DB는 운영 DB와 같은 종류라"로 화면에 드러냈다(분석용 DB가 원래 집계에 약하다는 일반론으로 읽히지 않게). 큰 집계가 '느리다'는 정도만 말하고 시간 수치는 쓰지 않았다. 장면 3 step 3의 느려짐은 데이터가 쌓인 것과 행 기반 구조가 겹친 결과로 썼다.
- Ch2의 분석용 DB와 웨어하우스의 차이를 장면 4 step 2 본문에서 한 문장으로 밝혔다(운영 DB의 표를 옮겨 온 곳 vs 분석하기 좋은 모양으로 다시 정리한 곳). 웨어하우스가 큰 집계에 빠른 이유는 열 기반 저장만이 아니다(여러 대가 나눠 계산하기, 메타데이터로 건너뛸 구역 고르기 등). 그래서 본문은 "비결 하나는 저장 방식"이라고 썼다.
- 행/열 저장 그림은 단순화했다. 실제 열 기반 저장은 행 묶음(row group) 단위로 열을 모으고, 메타데이터로 건너뛸 구역을 고르는 등 더 복잡하다. 압축은 사전 인코딩 한 가지만 그렸고 압축률 수치는 쓰지 않았다. 화면 고지: 장면 4 step 4 본문의 "실제로는 더 복잡하지만…" + 배지 "단순화한 그림".
- "많은 웨어하우스는 열 기반 저장을 써요"라고 썼다. '모든' 웨어하우스라고 하지 않았다.
- 정규화는 '중복을 줄이려 표를 나눈다'는 핵심만 다뤘다. 정규형(1NF, 2NF 등)은 다루지 않는다. 비정규화는 중복이 조금 생기는 대신 조인이 줄어든다는 트레이드오프로만 보여 줬다.
- 스타 스키마는 디멘션 3개(날짜·상품·고객)로 단순화했다. 실제로는 디멘션이 더 많고, 디멘션을 더 쪼갠 스노플레이크 스키마 같은 변형도 있다. 팩트의 한 행 = 주문 항목 1개(주문 1건이 아님)로 정했다. 상품 디멘션에 분류명을 함께 둔 것은 장면 5 step 2의 비정규화를 그대로 이은 것이고, 화면에 "step 2에서 합쳐 둠" 라벨로 연결했다.
- '키'는 Ch1 이후 별도 용어로 풀이하지 않고 "가리키는 번호(키)"로만 짧게 덧붙였다.
- SSOT는 '데이터를 한 군데에만 저장한다'가 아니라 '지표 정의를 한곳에서 관리하고 모두가 같은 정의를 쓴다'는 뜻으로 썼다(바이블 비트 그대로). 원래 SSOT는 '모두가 믿고 쓰는 기준 원천을 하나로 정한다'는 더 넓은 말이라, 풀이를 "지표 정의 같은 기준을 한곳에서 관리하는 원칙"으로 써서 지표 정의에만 쓰는 말로 좁혀 읽히지 않게 했다.
- '총매출'에 취소 주문까지 넣은 것은 바구니의 내부 지표 이름이다. 실제 회계의 총매출은 보통 취소된 주문을 넣지 않고, 취소까지 포함한 금액은 흔히 '주문 금액(거래액)'처럼 따로 부른다. 초보자가 '총매출 = 취소 포함'으로 외우지 않도록 화면 고지에 이 차이를 직접 적었다. 화면 고지는 장면 6 step 1의 "실제 회계의 총매출은 보통 취소된 주문을 빼요. 여기서는 바구니가 내부에서 정한 정의예요."가 맡는다.
- 맵의 model 노드는 warehouse와 bi 사이에 한 단계로 그렸지만, 실제로 dbt 같은 도구는 데이터를 따로 들고 있지 않고 웨어하우스에 SQL을 보내 그 안에서 지표 표를 만든다. BI는 그 결과 표를 웨어하우스에서 읽는다. 화면 고지: 장면 6 step 3 맵 아래 캡션 "실제로는 지표 계산도 웨어하우스 안에서 돌아가요. 맵에선 단계를 나눠 그렸어요." Ch7의 리니지(bi ← model ← warehouse)가 이 연결을 따르므로 연결선은 바꾸지 않았다.
- dbt는 대표 예시로만 두 문장 다뤘다. 변경 기록·검토는 dbt 자체 기능이라기보다 정의를 코드 파일로 두면 버전 관리·코드 리뷰를 쓸 수 있어서 생기는 장점이다. 그래서 본문도 기록·검토를 'Git 같은 버전 관리 도구에 둔 덕분'으로 썼다. 버전 관리는 바이블 0-9 용어 표에 없어 여기서 첫 등장 형식으로 풀이했다. 화면의 "총매출.sql" 파일 이름은 설명용이며 실제 SQL 코드는 보여 주지 않는다(바이블 0-9: Ch4는 SQL 조각 허용 챕터가 아님).
- BI 대시보드는 바이블 0-9 '용어 첫 등장 위치' 목록에 없어, 맵 라벨이 처음 바뀌는 이 챕터(장면 6 step 3)에서 풀이했다.
- 맵 연결 방식(warehouse → model → bi)은 바이블 0-7에 연결선 정의가 없어 구현 맵(src/content/map.ts)을 따랐다. 실제로는 오케스트레이터가 ETL 뒤에 지표 계산도 실행하지만, 맵에는 orch ⇢ etl 제어선만 그려 단순하게 두었다.
- 주니의 말투는 장면 6까지 Lv2("…하면 돼요."), 성장 연출의 레벨업 뒤 첫 한마디부터 Lv3("…하면 되는데, 이 부분은 조심해야 해요.")로 바꿨다.

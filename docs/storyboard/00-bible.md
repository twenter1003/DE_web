# 0. 스토리 바이블 (모든 챕터 공통 규칙)

이 문서는 각 챕터 스토리보드가 반드시 따르는 공통 설정이다. 여기 적힌 고유명사·노드·카드·수치는 임의로 바꾸지 않는다.

## 0-1. 무대: 쇼핑몰 스타트업 '바구니'

가상의 온라인 쇼핑몰. 생활용품을 판다. 실존 기업과 무관하다.

| 구간 | 사용자 수 (가상) | 챕터 |
|---|---|---|
| 막 문을 연 가게 | 100명 | Prologue, Ch1, Ch2 |
| 입소문이 남 | 1만 명 | Ch3, Ch4 |
| 전국구 쇼핑몰 | 100만 명 | Ch5, Ch6, Ch7 |
| 대형 플랫폼 | 1,000만 명 | Ch8, Ch9, Ch10, Epilogue |

회사 내부 수치(사용자 수, 주문 수, 로그 건수, 청구서 배수)는 이야기 속 가상 설정이라 써도 된다. 단, **현실 세계에 대한 주장**(예: "Parquet는 CSV보다 10배 빠르다", "기업의 80%가…")은 지어내지 않는다.

## 0-2. 등장인물

| 이름 | 역할 | 말투 |
|---|---|---|
| 주니 | 바구니의 첫 데이터 엔지니어(주인공). 비전공 신입으로 시작 | 레벨에 따라 변함(아래 0-3) |
| 윤 대표 | 바구니 대표 | 짧고 급함. "그래서 몇 개예요?" |
| 석 리드 | 개발 리드. 초반 조언자. 답 대신 힌트를 줌 | 담백함. "운영 DB에 직접요? 음…" |
| 태오 | 앱 개발자. 결제 페이지 담당, Ch7에서 이벤트 필드명을 바꿈 | 밝고 빠름 |
| 소라 | 마케터 (Ch4부터) | 열정적, 요청이 많음 |
| 민재 | 재무 담당 (Ch4부터) | 꼼꼼함, 정의를 따짐 |
| 다온 | 데이터 분석가 (Ch4에 합류). 후반엔 주니에게 질문하러 옴 | 호기심 많음 |
| 리아 | ML 엔지니어 (Ch10) | 논리적 |
| 새봄 | 에필로그의 새 신입 | Lv1 주니와 비슷 |

대명사 규칙: 인물을 '그/그녀'로 지칭하지 않는다. 이름이나 직함으로 부른다.

## 0-3. 주니의 성장 표현 (외모가 아니라 환경과 행동)

| 레벨 | 챕터 | 말투 예 | 책상 | 질문하러 오는 동료 | 주로 쓰는 표정 |
|---|---|---|---|---|---|
| Lv1 신입 | Prologue~Ch2 | "이거 어떻게 해요?", "일단 해볼게요!" | 노트북 한 대, 머그컵, 포스트잇 | 0명 (주니가 석 리드에게 감) | 당황, 집중 |
| Lv2 주니어 | Ch3~Ch4 | "이렇게 하면 돼요." | + 외장 모니터(화면에 작은 DAG) | 가끔 1명 | 집중, 뿌듯 |
| Lv3 미드레벨 | Ch5~Ch7 | "이렇게 하면 되는데, 이 부분은 조심해야 해요." | + 화이트보드(클러스터·레인 스케치), 듀얼 모니터 | 2명 | 집중, 뿌듯 |
| Lv4 시니어 직전 | Ch8~Ch9 | "먼저 왜 필요한지부터 확인해볼게요." | 화이트보드에 정돈된 아키텍처, 책 몇 권, 화분 | 3명 | 여유, 집중 |
| Lv5 시니어 | Ch10~Epilogue | "그건 지금 안 만들어도 돼요. 이유는요…" | 오히려 정돈됨: 모니터 하나, 화이트보드엔 단순한 그림 한 장, 옆에 멘티용 의자 | 여럿 + 새봄 | 여유 |

표정은 4종만 쓴다: **당황 / 집중 / 뿌듯 / 여유**.

## 0-4. 레벨

Lv1 신입 → (Ch2 끝) Lv2 주니어 → (Ch4 끝) Lv3 미드레벨 → (Ch7 끝) Lv4 시니어 직전 → (Ch10 클라이맥스) Lv5 시니어.
Ch10만 챕터 끝이 아니라 클라이맥스 장면에서 승급한다. Lv5는 새 기술을 배워서가 아니라 **안 만들기로 결정하는 순간** 일어난다.

## 0-8. 챕터 공통 구조 (순서 고정)

1. **오프닝** — 주니의 책상(레벨별 환경) + 문제를 꺼내는 대사 2~4줄. 스크롤 연동 아님.
2. **문제** — scrub 장면 (3~4 step)
3. **시도와 실패** — scrub 장면 (3~4 step). 주니가 순진하게 시도하고 실패한다.
4. **개념** — scrub 장면 1~2개: 비유 → 정확한 정의 → 쇼핑몰 예시. 필요한 곳에 "실제로는 더 복잡하지만…" 단순화 고지.
   - 인터랙션은 챕터당 최대 1개(아래 0-10).
5. **해결** — scrub 장면 (3~4 step). 맵에 노드가 추가되는 장면 포함.
6. **한 줄 요약** — 한 문장.
7. **퀴즈** — 1문항, 보기 3~4개, 정답 1개. 보기마다 해설(왜 맞고 왜 틀린지). 틀려도 해설을 보면 통과.
8. **성장 연출** — 카드 획득, 역량 변화, 맵 변화, (승급 챕터면) 레벨업, 주니의 한마디.

Epilogue는 퀴즈 없이: 줌아웃 → 새 신입 → 순환 → 도감 완성 → 처음부터 다시 보기.

분량: 챕터당 본문(내레이션+대사) 1,200~1,800자. 약 3분.

## 0-9. 글쓰기 규칙

- 내레이션: 친근한 해요체. **한 step의 텍스트 블록은 2~3문장**(대사 1~2줄은 별도로 붙일 수 있음). 문장은 짧게.
- 대사: 구어체, 한 줄 40자 안팎.
- 전문용어 첫 등장: `한글(English, 풀이)` 형식. 예: 멱등성(Idempotency, 여러 번 실행해도 결과가 같은 성질). 페이지 전체에서 처음 나오는 곳에서만. 다른 챕터에서 이미 풀이한 용어는 다시 풀지 않는다(아래 '용어 첫 등장 위치').
- 도구 이름은 "Airflow 같은 오케스트레이터"처럼 대표 예시로만. 설치법·문법 튜토리얼 금지. Ch1의 짧은 SQL, Ch7의 짧은 YAML 조각은 개념 설명용으로 허용.
- 과장·유행어·이모지 남발 금지. 느낌표는 대사에서만.
- 플레이스홀더(TODO, "여기에 설명") 금지. 완성된 문장만.
- 단순화한 곳은 반드시 밝힌다.

용어 첫 등장 위치(풀이는 여기서만):
데이터 엔지니어/분석가/사이언티스트·이벤트 로그·트랜잭션·정형/반정형/비정형·스키마 → Prologue / 데이터베이스·테이블·행·열·SQL·쿼리·JOIN·OLTP·OLAP → Ch1 / ETL·ELT·정제·결측치·배치·분석용 저장소 → Ch2 / 스케줄링·cron·의존성·DAG·오케스트레이터·재시도·멱등성·백필 → Ch3 / 데이터 웨어하우스·행 기반/열 기반 저장·정규화/비정규화·팩트·디멘션·스타 스키마·SSOT·dbt → Ch4 / 스케일 업/아웃·분산 처리·워커·Hadoop·Spark·데이터 레이크·오브젝트 스토리지·Parquet·파티셔닝·셔플·3V → Ch5 / 스트리밍·이벤트 브로커·Kafka·토픽·프로듀서·컨슈머·CDC·이벤트 시간/처리 시간·윈도우·exactly-once → Ch6 / 데이터 품질 테스트·신선도·스키마 변경·데이터 계약·리니지·모니터링·SLA·CI·YAML → Ch7 / 레이크하우스·오픈 테이블 포맷·트랜잭션(ACID)·스키마 진화·타임 트래블·메달리온·Upsert(MERGE) → Ch8 / 풀스캔·파티션 프루닝·스토리지 계층화·최소 권한·접근 제어·마스킹·가명처리·카탈로그·거버넌스 → Ch9 / 트레이드오프·Build vs Buy·ADR·Reverse ETL·Zero-ETL·멘토링 → Ch10

## 0-10. 인터랙션 (챕터당 최대 1개)

| 챕터 | 인터랙션 |
|---|---|
| Prologue | "가게 직접 이용해보기": 클릭·검색·장바구니·결제 버튼 → 데이터 입자가 생겨 이벤트 로그/트랜잭션으로 분류됨 |
| Ch1 | SQL 놀이터: 준비된 쿼리 조각(SELECT 열 / WHERE 조건 / GROUP BY / JOIN)을 고르면 결과 표가 바뀜. 실제 SQL 엔진 없음 |
| Ch2 | ETL ↔ ELT 토글: 컨베이어 스테이션 순서가 바뀜 |
| Ch3 | DAG 실패 시뮬레이터: 노드를 클릭해 실패시키면 하위 노드가 멈추고, 재시도 버튼으로 연쇄 진행 |
| Ch4, Ch6, Ch7, Ch9 | 없음(스크롤 장면만) |
| Ch5 | 워커 수 슬라이더: 처리 시간 = 단순화한 모델. 늘릴수록 빨라지다 조율·셔플 비용으로 효과가 줄어듦 |
| Ch8 | 타임 트래블 슬라이더: 테이블의 과거 버전(v1~v4) 되감기 |
| Ch10 | 트레이드오프 저울: '지연시간' 슬라이더를 낮추면 '비용'·'운영 복잡도' 막대가 치솟음 |
| Epilogue | 없음(맵 노드 클릭 → 해당 챕터로 이동은 전역 기능) |

인터랙션은 키보드로도 조작 가능해야 하고, 모션 축소 모드에서도 결과(표·막대·상태)가 바뀌어 배울 수 있어야 한다.

## 0-11. 비주얼 어휘 (모션 설명에 쓰는 공통 부품 이름)

- **노드**: 손그림 사각 박스 + 라벨 (선의 거칠기는 챕터가 갈수록 정밀해짐)
- **화살표**: 데이터 흐름(실선), 제어(점선), 제안(점선 + 흐린 색)
- **입자**: 강조색 작은 점·사각형. 데이터 한 건 = 입자 하나
- **표**: 행·열 DOM 표. 행 하이라이트, 열 하이라이트
- **코드 타이핑**: SQL·YAML이 한 글자씩 써짐(스크롤 연동)
- **게이지/미터기**: 서버 부하, 요금
- **상태 아이콘**: ✓ 성공(초록) / ✕ 실패(빨강) / ⏸ 대기(회색) / ↻ 재시도. 색만으로 의미를 전달하지 않는다
- **말풍선**: 인물 + 대사
- **주니**: 라인아트, 표정 4종

모션 규칙: 모든 모션은 개념 하나를 설명한다. 회전·바운스·패럴랙스 장식 금지. 각 step의 다이어그램 상태는 **정지 그림으로도 이해되어야 한다**(모션 축소 모드에서는 step마다 정지 그림 + 텍스트로 보여준다).

## 0-12. 정확성 메모 (틀리기 쉬운 지점)

- 이벤트 로그: "무슨 일이 일어났는지"의 기록(클릭, 검색, 페이지 조회). 양이 많고, 일부 유실돼도 서비스가 멈추진 않음. 트랜잭션 데이터: 주문·결제처럼 돈·재고 상태를 바꾸는 확정된 기록. 정확해야 함.
- 반정형: JSON처럼 구조는 있지만 고정된 표 형태는 아닌 것. 비정형: 텍스트·이미지·음성처럼 미리 정한 구조가 없는 것.
- OLTP: 짧은 읽기·쓰기를 아주 많이, 빠르게(주문 처리). OLAP: 많은 행을 훑어 집계(분석). 같은 DB에서 무거운 분석을 돌리면 운영이 느려질 수 있다.
- ELT: 원본을 먼저 적재(Load)하고, 분석용 저장소 안에서 변환(Transform). 저장·연산이 싸고 확장 쉬운 분석용 저장소가 보편화되며 많이 쓰이게 됐다. ETL이 틀린 게 아니라 순서의 선택.
- cron은 '정해진 시각에 실행'만 한다. 의존성·재시도·알림·이력 관리는 오케스트레이터의 몫. Airflow 자체는 데이터를 처리하는 엔진이라기보다 작업을 지휘하는 도구.
- 멱등성 구현 예: '그날 치를 지우고 다시 쓰기(파티션 덮어쓰기)', 고유 키 기반 Upsert. 무조건 덧붙이기(append)는 재실행 시 중복을 만든다.
- 열 기반 저장: 필요한 열만 읽고, 같은 종류 값이 모여 있어 압축이 잘 된다. 행 기반: 한 건을 통째로 읽고 쓰기 좋다(OLTP).
- 정규화: 중복을 줄이려고 테이블을 나눔(쓰기·일관성에 유리). 비정규화: 분석 편의·속도를 위해 일부러 합쳐 둠(조인 감소).
- 스타 스키마: 가운데 팩트(측정값·사건: 주문 항목, 금액) + 주변 디멘션(설명 속성: 상품, 고객, 날짜).
- Hadoop: 분산 파일 시스템(HDFS) + MapReduce. 중간 결과를 디스크에 많이 씀. Spark: 메모리를 적극 활용하고 더 유연한 처리 방식을 제공해 반복·복합 작업에 유리. **속도 배수 같은 수치 금지.**
- Parquet: 열 기반 파일 포맷, 압축 효율, 스키마(열 이름·타입)가 파일에 함께 저장됨. CSV: 사람이 읽기 쉽지만 타입 정보가 없고 필요한 열만 읽기 어려움.
- 파티셔닝(저장): 날짜 같은 키로 폴더/구역을 나눠, 쿼리가 필요 없는 구역을 건너뛰게(파티션 프루닝은 Ch9에서 비용 관점으로 다시). Kafka 파티션은 토픽을 나눈 '레인'으로 의미가 다르다 — Ch6에서 구분해서 말할 것.
- 셔플: GROUP BY·JOIN 때 같은 키의 데이터를 같은 워커로 모으려고 네트워크로 옮기는 과정. 네트워크·디스크 I/O 때문에 비싸다.
- 3V: Volume(양)·Velocity(속도)·Variety(다양성). 빅데이터를 설명하는 대표적인 틀.
- Kafka: 이벤트를 순서대로 기록해 두는 분산 로그. 프로듀서가 토픽에 쓰고, 여러 컨슈머가 각자 속도로 읽음. 순서는 **파티션 안에서만** 보장. 일정 기간 보관(retention).
- CDC: DB의 행 변경(삽입·수정·삭제)을 DB 변경 로그 등에서 읽어 이벤트로 흘려보내는 방식.
- exactly-once: 실제로는 '최소 한 번 전달 + 멱등 처리/트랜잭션'을 조합해 결과적으로 한 번 반영되게 만드는 경우가 많다. 공짜가 아니다.
- 이벤트 시간(사건이 일어난 시각) vs 처리 시간(시스템이 받은 시각). 늦게 도착한 데이터 때문에 윈도우를 언제 닫을지 정해야 한다.
- 품질 테스트: not null, 유일성(unique), 허용 범위(금액 ≥ 0), 신선도(freshness: 최근 데이터가 제때 들어왔는가).
- 데이터 계약: 데이터를 만드는 쪽과 쓰는 쪽이 스키마·의미·변경 절차를 미리 약속한 것.
- 오픈 테이블 포맷(Iceberg, Delta Lake 등): 오브젝트 스토리지의 파일들 위에 메타데이터 층을 둬서 트랜잭션(ACID), 스키마 진화, 타임 트래블을 가능하게 함. 레이크하우스가 언제나 정답은 아님.
- 메달리온: Bronze(원본 그대로) → Silver(정제·중복 제거·표준화) → Gold(비즈니스용 집계). 특정 업체가 널리 퍼뜨린 이름이지만 개념은 일반적.
- 가명처리: 식별자를 대체값으로 바꿈. 추가 정보와 결합하면 다시 알아볼 수 있으므로 여전히 보호 대상. 익명처리와 다르다. 법 조항 인용은 하지 않는다.
- 일부 클라우드 분석 서비스는 쿼리가 읽은 데이터 양만큼 과금한다("모든 서비스"라고 하지 말 것).
- Reverse ETL: 웨어하우스(또는 레이크하우스)에서 만든 결과를 CRM·광고·마케팅 툴 같은 운영 도구로 되돌려 보냄.
- Zero-ETL: 운영 DB 등의 데이터를 분석 저장소로 자동 복제해 주는 관리형 연동. 파이프라인을 직접 만들지 않는 선택지. 지원되는 조합이 제한적이고, 변환·품질·비용·특정 업체 종속 문제는 남는다. 내부적으로 CDC 같은 방식을 쓰기도 한다.
- ADR(Architecture Decision Record): 무엇을, 왜, 어떤 대안을 버리고 결정했는지 남기는 짧은 기록.

## 0-13. 복선과 회수

- Prologue의 주니: "데이터가 어디서 오는지부터 알아야겠어요." → Epilogue의 주니: "데이터가 어디서 오는지부터 볼까요?"
- Prologue의 비정형 데이터(리뷰·상품 이미지) → Ch5에서 레이크에 쌓이기 시작 → Ch10 ML 학습 데이터로 다시 등장
- Ch6 끝 혼잣말: "근데… 모든 게 실시간이어야 할까?" → Ch10 "15분 늦으면 의사결정이 달라지나요?"
- Ch1에서 주니가 석 리드에게 질문하러 감 → Ch10에서 다온이 주니에게 질문하러 옴, 주니는 답 대신 질문으로 이끔(멘토링)
- Ch3의 멱등성 → Ch6 exactly-once, Ch8 Upsert에서 다시 언급
- Ch4의 '매출' 단일 정의 → Ch7에서 그 정의가 지켜졌기에 원인 추적이 빨랐다

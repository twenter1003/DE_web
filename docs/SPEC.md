# 프로젝트: Data Engineering A to Z — 주니어에서 시니어까지

## 0. 역할과 진행 방식
너는 시니어 프론트엔드 엔지니어이자 모션 디자이너이고, 데이터 엔지니어링을 입문자에게 가르치는 교육 설계자다.
이 프로젝트는 한 번에 만들지 말고 '8. 진행 단계'의 Phase 순서대로 진행한다. 각 Phase가 끝나면 결과를 요약 보고하고 **멈춰서 내 승인을 기다려라.** 애매한 점은 합리적으로 가정하되, 가정한 내용을 보고에 적어라.

## 1. 무엇을 만드는가
데이터 엔지니어링을 전혀 모르는 사람(비전공자, 코딩 경험 거의 없음)을 위한 **스크롤 기반 모션그래픽 학습 웹페이지**.
가상의 신입 데이터 엔지니어 '주니'가 시니어로 성장하는 이야기를 따라가며 데이터 엔지니어링의 핵심 개념을 A부터 Z까지 배운다.

끝까지 본 사람은
1. 데이터 엔지니어가 하는 일을 한 문장으로 설명할 수 있다.
2. 각 핵심 개념이 **어떤 문제 때문에 생겼는지** 말할 수 있다.
3. 주니어와 시니어의 차이가 '아는 도구의 수'가 아니라 **판단력**(트레이드오프, 비용, 신뢰성, 단순함)이라는 걸 이해한다.

## 2. 핵심 컨셉: 회사의 성장 × 엔지니어의 성장
- 무대: 가상의 온라인 쇼핑몰 스타트업. 사용자 100명 → 1만 → 100만 → 1,000만으로 커진다.
- 회사가 커질 때마다 새로운 데이터 문제가 터지고, 주니는 그걸 해결하며 성장한다. **기술은 반드시 '문제의 해결책'으로 등장한다.** 문제 없이 도구부터 소개하지 않는다.
- 모든 챕터의 리듬: 문제 발생 → 주니의 시도와 실패 → 개념 설명(비유 → 정확한 정의 → 쇼핑몰 예시) → 해결 → 한 줄 요약 + 퀴즈 1문항(틀려도 해설을 보면 통과) → 성장 연출(카드 획득·역량 차트 상승, 승급 챕터에선 레벨업)
- 페이지 전체를 관통하는 장치 3가지
  1. **진화하는 파이프라인 맵**: 프롤로그에서 'CSV 파일 1개 + 노트북'뿐이던 다이어그램이 챕터마다 노드가 늘며 자라고, 에필로그에서 전체 데이터 플랫폼으로 줌아웃된다. 노드를 클릭하면 해당 챕터로 이동한다.
  2. **주니의 성장 표현**: 외모보다 환경과 행동으로 보여준다. 책상 위 장비, 화면 속 다이어그램의 복잡도, 말풍선 말투("이거 어떻게 해요?" → "이렇게 하면 돼요" → "그건 지금 안 만들어도 돼요. 이유는요…"), 동료들이 주니에게 질문하러 오는 빈도.
  3. **A–Z 용어 카드**: 챕터마다 알파벳 카드를 얻고, 26장을 모으면 도감이 완성된다. 카드 = 용어 + 한 줄 정의 + 등장 챕터.
- 레벨: Lv1 신입 → Lv2 주니어 → Lv3 미드레벨 → Lv4 시니어 직전 → Lv5 시니어. 작은 HUD에 레벨·진행도·카드 수를 보여주고, 클릭하면 도감과 역량 레이더 차트(SQL·모델링 / 파이프라인·자동화 / 대규모 처리 / 품질·운영 / 설계·판단 / 소통·리딩)가 펼쳐진다. 후반에는 기술 축보다 '설계·판단'과 '소통·리딩' 축이 크게 자라야 한다.
- **시니어의 정의 (가장 중요)**: 요구사항을 되묻고, 지연시간·비용·복잡도·신뢰성 사이의 트레이드오프를 판단하고, 때로는 '안 만드는 결정'을 내리고, 다른 사람을 성장시키는 사람. 후반부는 기술을 쌓는 장면이 아니라 **덜어내는 장면**이어야 하고, Lv5 승급은 새 기술을 배울 때가 아니라 안 만들기로 결정하는 순간에 일어난다.
- 엔딩: 시니어가 된 주니에게 새 신입이 CSV 파일 하나를 들고 찾아온다. "데이터가 어디서 오는지부터 볼까요?" → 첫 장면으로 순환.

## 3. 커리큘럼
- 챕터당 3분 안팎 분량. '가볍게'로 표시한 항목은 이름과 한두 문장 수준으로만 다룬다.
- 비유·모션·인터랙션·카드 용어는 예시다. 더 좋은 안이 있으면 Phase 0에서 제안해도 되지만 개념의 정확성은 바꾸지 않는다. 인터랙션은 챕터당 최대 1개.
- [Lv1→2]는 그 챕터 끝에서 승급한다는 뜻 (Ch10만 클라이맥스에서 승급)

**Prologue. 데이터는 어디서 오는가** [Lv1]
- 상황: 쇼핑몰이 문을 열고, 사용자들이 클릭·검색·장바구니·결제를 한다.
- 배울 것: 이벤트 로그 vs 트랜잭션 데이터, 정형/반정형/비정형, 데이터 엔지니어·분석가·사이언티스트의 역할 차이
- 비유: 데이터 엔지니어는 도시에 수도관을 놓는 사람, 분석가·사이언티스트는 그 물로 요리하고 실험하는 사람
- 모션: 사용자 행동 하나하나가 데이터 입자가 되어 쏟아지고, 형태별로 분류된다
- 카드: S(Schema), U(Unstructured data)

**Ch1. "어제 몇 개 팔렸어요?" — SQL과 데이터베이스** [Lv1]
- 상황: 대표의 질문에 주니가 운영 DB에 직접 SQL을 날린다 → 분석 쿼리 때문에 결제 페이지가 느려진다.
- 배울 것: 테이블·행·열, SELECT/WHERE/GROUP BY/JOIN, OLTP vs OLAP(운영용과 분석용을 분리해야 하는 이유)
- 모션: SQL이 타이핑되면 해당 행이 하이라이트되고 집계되어 숫자 하나로 모인다. 동시에 서버 부하 게이지가 치솟는다
- 인터랙션: 준비된 쿼리 조각을 고르면 결과 표가 바뀌는 'SQL 놀이터' (실제 SQL 엔진은 쓰지 않는다)
- 카드: J(Join), O(OLTP vs OLAP)

**Ch2. 첫 파이프라인 — ETL과 배치** [Lv1→2]
- 상황: 운영 DB를 건드리지 않으려고 매일 밤 데이터를 복사·정리해 분석용 저장소로 옮긴다.
- 배울 것: Extract·Transform·Load, ETL vs ELT, 정제(중복·결측치·타입), 배치 처리
- 비유: 택배 물류센터 — 수거 → 분류·포장 → 배송
- 모션: 울퉁불퉁한 데이터 블록이 컨베이어 벨트의 세 스테이션을 지나며 반듯해진다. ETL↔ELT 토글 시 스테이션 순서가 바뀐다
- 카드: E(ETL/ELT), B(Batch)

**Ch3. 새벽 3시의 장애 — 자동화와 오케스트레이션** [Lv2]
- 상황: cron으로 자동화했는데 새벽에 실패해도 아무도 몰랐다. 다시 돌렸더니 데이터가 두 번 들어갔다.
- 배울 것: 스케줄링, 작업 의존성과 DAG, 오케스트레이터(Airflow 등), 재시도·알림, 멱등성 / 가볍게: 백필
- 비유: 요리 순서 — 밥이 다 돼야 비빔밥을 만들 수 있다
- 모션: DAG가 그려지고, 노드 하나가 실패하면 하위 노드가 회색으로 멈췄다가 재시도 후 초록으로 연쇄 진행된다. 멱등/비멱등 재실행 결과를 나란히 비교
- 인터랙션: 노드를 클릭해 일부러 실패시켜 보는 시뮬레이터
- 카드: A(Airflow), D(DAG), I(Idempotency)

**Ch4. 매출이 두 개예요 — 웨어하우스와 데이터 모델링** [Lv2→3]
- 상황: 마케팅팀과 재무팀이 말하는 '매출'이 서로 다르다.
- 배울 것: 데이터 웨어하우스, 행 기반 vs 열 기반 저장(분석이 빠른 이유), 정규화/비정규화, 팩트·디멘션과 스타 스키마, 지표 정의를 한곳에서 관리하는 이유(Single Source of Truth) / 가볍게: SQL 변환 도구(dbt 등)
- 비유: 서가와 색인이 잘 정리된 도서관
- 모션: 행 저장 vs 열 저장 — 필요한 열만 빛줄기가 훑고 지나간다. 팩트 테이블을 중심으로 디멘션 테이블이 별 모양으로 배치된다
- 카드: F(Fact table), N(Normalization), W(Warehouse)

**Ch5. 데이터가 노트북에 안 들어가요 — 빅데이터와 분산 처리** [Lv3]
- 상황: 사용자 100만, 하루 로그 수억 건. 스크립트가 메모리 부족으로 죽는다.
- 배울 것: 스케일 업 vs 스케일 아웃, 분산 처리(Hadoop에서 Spark로 이어진 흐름), 데이터 레이크와 오브젝트 스토리지, CSV vs Parquet, 파티셔닝 / 가볍게: 셔플이 비싼 이유
- 비유: 책 1만 권을 혼자 세기 vs 100명이 나눠 세고 합치기
- 모션: 거대한 블록이 조각나 여러 워커에게 나뉘고, 병렬로 처리된 뒤 합쳐진다. 날짜별 파티션 폴더 중 필요한 것만 열린다
- 인터랙션: 워커 수 슬라이더 — 늘릴수록 빨라지다가, 조율·데이터 이동(셔플) 비용 때문에 효과가 줄어드는 지점이 보인다
- 카드: H(Hadoop), P(Partitioning), V(3V: Volume·Velocity·Variety)

**Ch6. 지금 이 순간 — 스트리밍** [Lv3]
- 상황: "이상 결제를 실시간으로 잡아주세요", "타임세일 재고를 실시간으로 보고 싶어요"
- 배울 것: 배치 vs 스트리밍, 이벤트 브로커(Kafka 등)와 프로듀서/컨슈머, CDC / 가볍게: 이벤트 시간 vs 처리 시간, 윈도우, 늦게 도착한 데이터, 정확히 한 번(exactly-once) 처리
- 비유: 물을 양동이에 모아 하루 한 번 옮기기(배치) vs 수도꼭지에서 계속 흐르는 물(스트리밍)
- 모션: 토픽 파티션은 레인으로, 이벤트는 레인을 따라 흘러 5분 단위 상자(윈도우)에 담긴다
- 복선: 챕터 끝에 주니가 혼잣말한다 — "근데… 모든 게 실시간이어야 할까?" (Ch10에서 회수)
- 카드: C(CDC), K(Kafka), X(eXactly-once)

**Ch7. 월요일 아침, 매출이 0원 — 데이터 품질과 운영** [Lv3→4]
- 상황: 경영 회의 직전 대시보드 매출이 0원. 원인은 앱 업데이트로 이벤트 필드명이 바뀐 것.
- 배울 것: 품질 테스트(null·유일성·범위·신선도), 스키마 변경과 데이터 계약, 리니지, 모니터링·알림 / 가볍게: SLA, 코드 리뷰·CI로 변경을 배포 전에 잡기. 핵심 메시지: 조용히 틀리는 데이터가 시끄럽게 실패하는 것보다 위험하다
- 모션: 숫자가 0으로 떨어짐 → 리니지 그래프를 거꾸로 거슬러 올라가 원인 노드를 찾는다 → 파이프라인 곳곳에 검문소가 설치된다
- 카드: L(Lineage), Q(Quality), Y(YAML — 테스트·설정을 코드로 선언)

**Ch8. 호수와 창고를 합치다 — 레이크하우스** [Lv4]
- 상황: 데이터 레이크(싸지만 어수선함)와 웨어하우스(깔끔하지만 비쌈)에 같은 데이터가 두 벌씩 있다.
- 배울 것: 레이크하우스, 오픈 테이블 포맷(Iceberg·Delta Lake 등)이 주는 트랜잭션·스키마 진화·타임 트래블, 메달리온 아키텍처(Bronze→Silver→Gold) / 가볍게: Upsert(Merge)
- 비유: 정수 처리 — 원수 → 정수 → 병에 담긴 생수
- 모션: 세 층이 쌓이며 데이터 색이 탁한 색에서 맑은 색으로 바뀐다
- 인터랙션: 타임 트래블 슬라이더로 테이블의 과거 버전 되감기
- 카드: M(Medallion), T(Time travel)

**Ch9. 청구서와 개인정보 — 비용·보안·거버넌스** [Lv4]
- 상황: 클라우드 비용이 3배가 됐고, 개인정보가 담긴 테이블이 전사에 열려 있었다.
- 배울 것: 비용 최적화(풀스캔 vs 파티션 프루닝, 스토리지 계층화), 최소 권한 원칙과 접근 제어, 개인정보 마스킹·가명처리 / 가볍게: 데이터 카탈로그, 거버넌스
- 모션: 쿼리가 테이블 전체를 훑는 동안 요금 미터기가 빠르게 돈다 vs 필요한 파티션만 읽어 거의 안 움직인다. 개인정보 열에 모자이크가 덮인다
- 카드: G(Governance)

**Ch10. 시니어가 되는 순간 — 판단, 설계, 그리고 안 만드는 용기** [Lv4→5]
- 상황: 동시에 들어온 요청 — "실시간 대시보드 만들어주세요", "새 툴 도입하죠", "ML팀이 학습 데이터가 필요해요"
- 배울 것: 요구사항 되묻기("15분 늦으면 의사결정이 달라지나요?"), 트레이드오프, Build vs Buy, 멘토링 / 가볍게: 설계 문서와 의사결정 기록(ADR), 웨어하우스의 결과를 CRM·마케팅 툴로 되돌려 보내는 Reverse ETL, ML·AI를 위한 데이터(프롤로그의 비정형 데이터가 다시 등장)
- 인터랙션: 트레이드오프 저울 — '지연시간'을 낮추면 '비용'과 '운영 복잡도' 막대가 치솟는다
- 클라이맥스: 주니가 실시간 대신 15분 배치를 제안하자 파이프라인 맵에서 불필요한 노드가 사라지며 맵이 오히려 단순해지고, 이 순간 Lv5로 승급한다
- 카드: R(Reverse ETL), Z(Zero-ETL — 파이프라인을 직접 만들지 않는 선택지. 만능이 아니라는 점도 함께)

**Epilogue. 다시 A부터** [Lv5]
- 전체 플랫폼으로 줌아웃 → 새 신입 등장 → 첫 장면으로 순환. 도감 완성 연출과 '처음부터 다시 보기' 버튼.

## 4. 비주얼·모션 방향
- 콘셉트 **'스케치에서 설계도로'**: 초반은 손으로 그린 듯한 거친 선, 후반으로 갈수록 선이 정밀해져 시니어 단계에선 정확한 기술 설계도(블루프린트)가 된다. 선의 정밀도 자체가 성장을 표현한다. 배경도 종이 톤에서 남색 블루프린트 톤으로 서서히 바뀐다. (구현 예: rough.js의 roughness를 챕터 진행에 따라 낮추고, seed를 고정해 리렌더링 때 선이 떨리지 않게)
- 색: 데이터 입자는 강조색 하나로 통일, 실패는 빨강, 성공은 초록. 색만으로 의미를 전달하지 말고 아이콘·텍스트를 함께 쓴다. 배경이 바뀌는 모든 구간에서 텍스트 대비는 WCAG AA 이상.
- 폰트: 본문 Pretendard, 코드·라벨 JetBrains Mono
- 캐릭터: 단순한 라인아트 SVG, 표정 3~4종(당황·집중·뿌듯·여유)
- 첫 화면: 5초 안에 '무엇을 배우는지', '스크롤하면 이야기가 진행된다', 예상 소요 시간이 전달되게
- 반응형: 데스크톱 경험을 먼저 설계하되, 모바일에선 다이어그램을 세로로 재배치하고 모션을 단순화해도 된다
- 금지: 보라색 그라디언트 + 글래스모피즘 같은 흔한 템플릿 스타일, 이유 없는 패럴랙스·회전·바운스, 실제 기업·오픈소스 로고 이미지(도구 이름은 텍스트 라벨로만)

모션 원칙 (반드시 지킬 것)
1. 모든 애니메이션은 개념 하나를 설명해야 한다. 설명하지 않는 장식 모션은 넣지 않는다.
2. 학습자가 속도를 통제한다. 핵심 설명은 스크롤 연동(scrub) + 핀 고정 방식의 단계형 장면으로 만들고, 자동 재생 애니메이션에는 다시 보기 버튼을 둔다.
3. 스크롤 하이재킹 금지. 브라우저 기본 스크롤 속도를 바꾸지 않고, 핀 고정 구간은 짧게 유지한다.
4. 한 화면에 개념 하나, 텍스트 블록은 2~3문장 이내.
5. `prefers-reduced-motion`을 존중하고 페이지 안에도 '모션 줄이기' 토글을 둔다. 모션을 꺼도 정적 다이어그램과 단계별 텍스트로 모든 내용을 배울 수 있어야 한다.

## 5. 콘텐츠 작성 규칙
- 톤: 설명은 친근한 해요체, 캐릭터 대사는 구어체
- 전문용어는 첫 등장 시 한글 풀이와 영어를 함께 쓴다. 예: 멱등성(Idempotency, 여러 번 실행해도 결과가 같은 성질)
- 개념 중심. 도구 이름은 대표 예시로만 소개하고, 설치법·문법 튜토리얼은 넣지 않는다.
- 근거 없는 수치·통계를 지어내지 않는다. 단순화한 부분은 "실제로는 더 복잡하지만…"처럼 단순화했다고 밝힌다.
- 본문·대사·퀴즈·카드 정의 등 모든 텍스트는 코드와 분리된 콘텐츠 파일에 둬서, 컴포넌트를 건드리지 않고 문구만 고칠 수 있게 한다.

## 6. 기술 스택
- Vite + React + TypeScript
- GSAP + ScrollTrigger (`@gsap/react`의 `useGSAP`로 정리 처리), 필요하면 DrawSVG·MorphSVG 플러그인
- 반응형·모션 축소 분기는 `gsap.matchMedia()`로 처리
- 다이어그램·캐릭터는 인라인 SVG. 텍스트는 DOM에 둔다(캔버스에 글자를 굽지 않는다)
- Tailwind CSS + CSS 변수 기반 디자인 토큰
- 진행도·카드 수집은 localStorage에 저장하되, 실패해도 페이지가 정상 동작하게 try/catch
- 정적 빌드로 GitHub Pages나 Vercel에 배포할 수 있어야 한다
- 3D 엔진, 브라우저 SQL 엔진 같은 무거운 라이브러리는 넣지 않는다. 꼭 필요하면 이유를 먼저 보고하고 지연 로딩한다

## 7. 코드 구조 원칙
- 챕터 = 독립 컴포넌트 + 자체 타임라인. 데이터 입자, 파이프라인 노드, 캐릭터, 코드 타이핑, 표, 퀴즈 카드 등은 공통 컴포넌트로 재사용
- 콘텐츠는 `src/content/` 아래 챕터별 파일로
- 파이프라인 맵에 어떤 노드를 보여줄지는 챕터 진행도에서 파생
- ScrollTrigger 인스턴스는 언마운트 시 반드시 정리(중복 트리거·메모리 누수 방지)
